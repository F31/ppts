# ppts 架构审视与优化方案（2026-09-25）

> 审视范围：Go 后端（~5.2 万行 / 246 文件 / 27 个 internal 包）+ React 前端（~1.2 万行 / 49 文件）。
> 方法：静态勘察 + 现有测试实测 + 关键结论逐条复核。**所有结论附 `file:line` 证据**；未亲自核实的标注「代理勘察」。
> 一句话结论：**系统在产品能力上已经相当完整，主要风险不在"缺功能"，而在"复制实现造成的漂移"与"依赖缺失时的假成功"。**

---

## 0. 执行摘要

| 维度 | 评级 | 判据 |
|---|---|---|
| 分层解耦 | **C** | `internal/api` 里 25/31 个文件不经过 `app` 层，直连领域 store；甚至自带裸 SQL（authstore/authhandlers） |
| 组件化 / 复用 | **C** | 10 个领域包各有一份 PG + SQLite 实现，约 **6954 行**（占这些包 **72%**）逐句复制；前端 3 套分页、29 处"空态"混用三态 |
| 可靠性 | **C+** | 加固已经起步（RLS 双策略、`tenant.Run`、RoundTrip 幂等清理），但存在 **TTS 静默回落 fake**、**认证 fail-open**、**渲染器缺失静默降级**三处高危假成功 |
| 可扩展性 | **B-** | 多租户隔离下沉到 store 层是对的；但限流是单进程内存实现、调度并发上限只落在 PG 侧、worker 租约硬编码 30s 不可配 |
| 易用性 / 可运维 | **C** | 已有结构化日志 + OTel + Prometheus；但 `/healthz` 是假活、`/debug/vars` 裸奔、无 pprof、CI 不跑 `i18n:check`、基线 `go test` 实际漏跑约 107 个 pg 用例 |
| 功能完整性 | **B** | 导入解析→讲稿→配音→时间轴→播放→导出→成品库→分享 主链路闭合；缺口集中在 TTS 对齐真值、孤儿对象回收、前端类型契约 |

### 本次审视直接发现并修复的 P0

**`internal/artifact/sqlite.go` 列清单与 Scan 顺序错位（本次已修 + 补测试 + 负测验证）**
新增 `revision_no / source_display_name` 时，列追加在 `created_at` 之后，Scan 目标却插在 `&created` 之前：

- 后果不是静默错值，而是**硬失败**——负测实测报错：
  `Scan error on column index 10, name "created_at": converting driver.Value type string (...) to a int: invalid syntax`
  即 **SQLite 单租户部署下，成品的 Create / Get / ListByProject 全部报错**（成品库不可用、导出任务会在已插行之后失败）。
- 为什么没被发现：该包此前**只有 PG 测试**（`internal/artifact/` 无 sqlite 测试），而 compose 里 `cmd/ppts/compose.go:156` 明确装配 `artifact.NewSQLiteStore`。
- 修复：统一列清单顺序与 Scan 顺序（`sqlite.go:21-34`），并新增 `internal/artifact/sqlite_test.go` 做四列往返断言；已做**反向验证**（故意还原错位 → 测试立刻变红）。

这条缺陷本身就是**"双份实现 + 无 cross-profile 测试"这一结构性问题的实证**，下文把它列为第一优先治理项。

## 1. 分层解耦

### 1.1 依赖方向

**好消息**：无包级循环，`internal/app` 不依赖 `internal/api`，且 `internal/api` 内 **0 处**绕过 RLS（租户隔离下沉到 `tenant.Run`，`internal/tenant/db.go:20` 设 `app.tenant_id`），这是正确的架构决策。

**问题 1：上层绕过应用层直连 store**
- `internal/api/server.go:98` `NewHandler(projects project.ProjectStore, uploads upload.Store, scripts narration.Store, jobs JobStore, ...)` —— 领域 store 直接注入 HTTP 层。
- 31 个 api 源文件中 **25 个对 `app.` 的调用为 0**：`editor.go:24-25`（project 34 处、pipeline 12、narration 13）、`collab.go:16-17`（project 22 处）、`job.go:12-15`（pipeline 30 处）、`script.go:74` 直接持有 `narration.Store`。
- **影响**：`app`（3033 行）相对 `api`（9208 行）名存实亡；事务边界、配额、审计等横切逻辑无处收口，同一规则在两处各写一遍。

**问题 2：API 层自带裸 SQL，形成第二套写入路径**
- `internal/api/authstore.go:20` 持有 `*pgxpool.Pool`，:57/:61/:73/:98/:127/:177 直接 `DELETE/INSERT auth_tokens`。
- `internal/api/authhandlers.go:266-315` 一个事务内 6 条裸 SQL 建租户（tenants / users / user_profiles / tenant_members / credentials）。
- **影响**：绕过 `internal/tenant`（lifecycle/policy），RLS 策略与租户生命周期校验可被跳过。

**问题 3：用例层内嵌持久化**
- `internal/app/scriptsource.go:56-69`、`internal/app/voicesettings.go:66/94 vs 110/128` 在 `app` 包里又实现了两套 PG/SQLite store；表（`slide_script_sources`、`project_voice_settings`）不归属任何领域包。

**建议**
1. 建立规则：**`api` 只依赖 `app` service + 少量只读 query 接口**，路由注册改为注入 service。
2. 把 `authStore` / 租户创建下沉为 `internal/identity`（或并入 `internal/tenant`），禁止 api 持有 `*pgxpool.Pool`。
3. `app/scriptsource.go`、`app/voicesettings.go` 的 store 下沉到 `internal/scriptmeta`（或并入 `project`/`narration`）。

### 1.2 API 双轨（Connect RPC + 原生 HTTP）

| 类别 | 数量 | 位置 |
|---|---|---|
| Connect Service Handler | 8 service / **40 方法** | `internal/api/server.go:125-146` |
| 原生 HTTP 路由 | **96 条** / 16 文件 | 各 `registerXxxRoutes`（editor 18、tagfolder 12、server 11、public 10、collab 9…） |

同一能力的双写至少有 6 组：成员列表（`tenant.go:68` vs `memberlist.go:20`）、成品读取（`export.go:90` vs `artifact.go:26/29/34`）、任务详情（`job.go:54,72` vs `jobdetail.go:82`）、讲稿读写（`script.go:171-252` vs `server.go:226`）、配音估算（`narration.go:360` vs `:395,398`）、播放清单（`playback.go:185` vs `public.go:54`）。

**根因**：环境无 protoc/buf，新能力被迫走原生 HTTP。这是合理的历史选择，但**必须记账与回收**，否则契约持续分叉（前端也随之出现 `getPlaybackManifest` 手写 fetch 打 Connect 路径、`publishWork` 用 `connectJSON` 打 REST 路径的错用）。

**建议**：以 Connect 为唯一契约；96 条原生路由登记「回收清单」，按业务分组限期迁移或**显式豁免并说明理由**；新能力即使手工补 `.pb.go` 也走 proto。短期先消灭 6 组双写和两处前端调用错用。

### 1.3 请求校验与错误出口

- 校验完全散落：`internal/api` 非测试代码 **120 处 `TrimSpace(` + 117 处 `== ""`**；`editor.go:1258-1271` 与 `:1339-1352` 逐行重复。
- 错误体三套并存：Connect JSON（`narration.go:476`）、纯文本 `http.Error`（`acl.go:91,96,102`、`artifact.go:57,67`）、**业务失败返 200 + 体内 error**（`message.go:205`）。后者会让前端把失败当成功处理。

**建议**：抽 `decodeJSON / requirePath / requireIntQuery` 三个 helper 收敛 240 处手写校验；统一"业务失败一律 `writeConnectError`"。

## 2. 组件化与复用

### 2.1 后端：双份 store 是最大技术债（量化）

| 包 | PG | SQLite | 合计 | 占包比例 | 逐字相同行 |
|---|---|---|---|---|---|
| pipeline | 895 | 781 | 1676 | 69% | **412** |
| project | ~936 | 862 | ~1798 | 71% | — |
| narration | 397 | 420 | 817 | 88% | 184 |
| gateway | 408 | 400 | 808 | 66% | **278** |
| usage | 279 | 281 | 560 | 83% | 136 |
| artifact | 158 | 129 | 287 | 79% | 53 |
| 其余 4 包 | — | — | ~1008 | 59-84% | — |
| **合计** | | | **≈6954 行** | **≈72%** | |

特征：
- 列清单各写一份（`pipeline/postgres.go:43` ↔ `sqlite.go:39`，17 列）；
- 排序/游标规格复制且已漂移（`jsonb_array_length` vs `json_array_length`，`postgres.go:716` ↔ `sqlite.go:663`）；
- 语义漂移：`usage/postgres.go:85` 用 `INSERT … RETURNING`，SQLite 侧（`sqlite.go:93 + :124`）改为 INSERT 后二次 SELECT；`postgres.go:76` 插 `tenant_quotas` 不带 `updated_at`，`sqlite.go:83` 带；
- 跨文件隐式耦合（无 build tag，两份永远同时编译）：`sqlite.go:686` 调用 postgres.go:736 的 `decodeJobCursor`、`usage/sqlite.go:249` 调用 `usage/postgres.go:270` 的 `monthRange`；
- 编译期一致性断言不齐：`var _ Store = (*SQLiteStore)(nil)` 仅 9 个包有，**PG 侧只有 `messaging/postgres.go:298` 一份**，`project` 两侧都没有（其 36 vs 35 个方法的差异当前完全不可见）。

**建议（按性价比排序）**
1. **立刻**：给这 10 个包各补一份「SQLite 往返测试」（模板见本次新增的 `internal/artifact/sqlite_test.go`：覆盖 Create/Get/ListByProject/ListAll 四条读路径，并已用「故意还原错位」的负测证明它能拦住该类缺陷）。成本约 1-2 人日，可把"编译期不可见"变成"CI 立刻红"。
2. **短期**：统一列清单为单一常量 + 方言适配（占位符转换 `$n` ↔ `?`），并用 golden 测试比对两侧 SQL 输出。
3. **中期**：抽取 amb 或者用 `database/sql` + 占位符适配统一到一份实现，SQLite 方言差异集中在适配器。
4. 每个包两侧都补 `var _ X = (*PGStore)(nil)` 与 `(*SQLiteStore)(nil)`。

### 2.2 前端：单体页面 + 手工复制

- `ProjectEditor.tsx` **2079 行 / 36 useState / 18 useEffect / 13 useCallback**，聚合了"版本元信息、备注、页面列表、播放清单、缩略图探测、活跃任务、讲稿批量、语音属性、一键成稿、LLM 改写、词典、导出、冲突合并、讲稿栏拖拽"等十余个职责。已抽出 `ScriptEditor` / `Player` / `ExportDialog`，但页面层仍是单体。
- 推荐拆分顺序（收益/风险）：① 语音抽屉（1801-1916）② 一键成稿抽屉（1918-2038，自带 2s 轮询，拆出即卸载）③ 讲稿空态区（1695-1780）④ 页面轨 + 备注编辑器（1539-1626）⑤ 生成流程抽 `useScriptGeneration` / `useNarrationGeneration` hook。
- **重复模式**：空态 `<p className="empty-state">` **29 处**（且普遍把 loading / error / empty 三态渲染成同一外观，如 `Home.tsx:371-373`、`SettingsTags:150,181,217`、`Jobs:511,762`）；失败态 `load-failure`+`form-error` **~28 处**；表单行 28 处；手写模态框 9 处；**3 套分页**（`Jobs.tsx:35,328`、`Home.tsx:148`、`api.ts:419`）各写各的。
- 已有良好基准可直接推广：`Jobs.tsx:226-283`（条件轮询 + SSE + 指数退避 + abort）是**唯一规范实现**；`SettingsUsage.tsx:135-173` 是失败态/空态分离的正确写法。

**建议**：`<AsyncState>` / `<LoadFailure onRetry>` / `<EmptyState>` / `<Pager>` / `<Modal>` 五个基础组件 + 统一替换（约 2-3 人日）；轮询收敛为 `useJobPolling(jobId,{intervalMs,timeoutMs,onDone})`，以 Jobs.tsx 为蓝本。

## 3. 可靠性

### 3.1 高危：依赖缺失时的"假成功"

| # | 问题 | 证据 | 危害 |
|---|---|---|---|
| R1 | **TTS 默认回落 fake provider** | `cmd/ppts/worker.go:366-378`：`switch PPTS_TTS_PROVIDER { case "siliconflow": …; default: return tts.NewFakeProvider() }`；`internal/integrations/tts/fake.go:8-11` 产出静音 WAV；`docker-compose.yml:65` 显式 `fake`，而 `Dockerfile.worker` 根本不设该变量 | 变量**未设置/拼错/未知值**三种情况一律静默静音；配音 job 判 succeeded，用户拿到无声视频，且 `ppts_tts_synthesis_total` 计入 succeeded → **指标也假** |
| R2 | **认证 fail-open** | `cmd/ppts/server.go:169-185` JWT/OIDC 均未配 → `return nil, nil`；`internal/api/server.go:121` `allowDevHeaders := opt.Auth == nil`；`internal/api/auth.go:92-103` 凭 `X-PPTS-Tenant-ID` + `X-PPTS-User-ID` 即可成为任意租户任意用户；`docker-compose.yml:37-38` 明文硬编码 JWT secret / pepper | 生产漏配 secret 即**全站鉴权失效**，且无启动告警 |
| R3 | **LibreOffice 缺失静默降级** | `cmd/ppts/worker.go:80-85` 仅 Info 日志、不挂渲染器；`internal/app/ingest.go:136-139` `if h.renderer == nil … { return }` 解析照常成功；而 `render/render.go:25` 自称"不可用时显式报错" | 解析"成功"但无预览图/播放帧/导出素材，用户侧零信号（无 counter、无 step 标记） |
| R4 | **跨租户写入面**（代理勘察） | `memberlist.go:64,84` 只校验调用方是本租户 Admin，目标 `userId` 直传 `SaveProfile`；`user_profiles` **无 tenant_id、显式不启用 RLS**（`migrations/0030_user_profiles.sql:6`）；`membership/postgres.go:113-125` 直连 pool | 本租户 Admin 可改写已知的其他租户用户档案 |
| R5 | **`/ppts/object` PUT/DELETE 无 auth** | `internal/api/server.go:247,250,253` 挂载时未套 `auth()` | 写/删对象仅靠签名，强度待核实 |
| R6 | **`/debug/vars` 裸奔** | `internal/api/server.go:108` 直接挂 `expvar.Handler()`（`/metrics` 有 `PPTS_METRICS_TOKEN` 保护） | 暴露全量内部计数，含认证事件分布 |

> R1/R2/R3 已由我亲自复核代码确认；R4-R6 为代理勘察结论，R5 的签名强度、R4 的可达性建议二次验证后再定级。

**统一治理原则**：凡是「外部依赖不可用 → 用兜底继续跑」的地方，必须同时满足三件事——**显式开关**（默认关闭或仅本地 profile 允许）、**启动告警**（Warn + 指标）、**产物留痕**（例如解析结果写 `renderer: "unavailable"`，前端据此提示）。

### 3.2 任务管线

状态机 9 态（`pipeline/model.go:18-28`），PG 侧用 `FOR UPDATE SKIP LOCKED`（`postgres.go:173-209`）与 SECURITY DEFINER 函数 `ppts_claim_next_job`（`migrations/0018:7-73`），SQLite 侧靠进程内互斥（`worker.go:46,140-141`，无 SKIP LOCKED）。薄弱点：

- **租约 30s 硬编码且无 env 覆盖**（`worker.go:88`），心跳 10s（`:99-101`）。narration / MP4 导出远超 30s；遇 GC 停顿或 DB 抖动即被其他 worker 重领，**两个 worker 跑同一任务**。
- **重领会 `attempt+1`**（`postgres.go:190`）→ 崩溃-重领循环快速耗尽 10 次配额并提前判死。
- `Run` 遇瞬时错误直接返回（`worker.go:133-135`）→ 一次网络抖动即**整个 worker 退出**。
- **外部调用不幂等**：TTS `LogicalOpID` 仅注释为追踪用途（`internal/integrations/tts/tts.go:56`），siliconflow 实现未用作供应商幂等键 → 崩溃重试必然**重复合成、重复付费**（用户侧额度因 `Settle` 幂等不会重复扣，钱照付）。
- **非内容寻址的 StepKey**：`scriptdraft.go:129` `"page:v1:"+slideID` 与 `ingest.go:142` 均不含 revision / 内容哈希 → 内容变更后重跑会命中旧成功态；`MarkStep` 无条件 upsert（`postgres.go:411-419`）还可让状态从 success **倒流**为 failed。

### 3.3 配额与清理

- 额度释放只在"取消"路径（`api/job.go:130-138`，且 error 被完全忽略）与 24h TTL 兜底（`cmd/ppts/worker.go:194` + `retention/postgres.go:177-199`）；**任务失败路径无任何 Release**（`app` 层 grep 无 Release）。
- **SQLite 模式不启动清扫循环**（`cmd/ppts/worker.go:157-159`）→ 预占永不回收。
- 孤儿对象：`retention` 派生清理白名单只有 `artifact/audio/render`（`retention/postgres.go:125-130`），实际 asset_type 还有 timeline/subtitle/segments/alignment/document/notes/work/source；而时间轴键含 `job.ID`（`app/narration.go:568`）→ **每次重生成都产生永不回收的新对象**。全仓无"对象存在但库内无引用"的孤儿扫描。

### 3.4 双迁移

- 均以完整文件名为版本键（`internal/migrate/migrate.go:29-34,45-49,60`；SQLite `internal/db/sqlite.go:81-101`），因此 PG 侧 `0008`×2、`0009`×2 并存可行。
- 但 **PG 47 个 vs SQLite 13 个**：RLS、usage/quotas、retention、audit、角色/调度函数、job events、jobs 系列索引等 **34 项只存在于 PG**；SQLite `0001_init.sql`(19.7KB) 一次性建 28 张表合并了 PG 0002-0034 的大部分内容。
- 内容漂移：`0040_script_source_revision.sql`(1082B) vs sqlite `0008`(3412B)；`0043_accounts_phone_verification.sql`(5133B) vs sqlite `0012`(1628B)。
- SQLite 编号从 0010 跳到 0012（缺 0011，原因未核实）。
- `migrate.go:43-66` 用 `SELECT EXISTS` 判重后应用，**无 `pg_advisory_lock`** → 多副本/并行执行存在交错风险。

## 4. 可扩展性

- **多租户底座是对的**：RLS 双策略 + `tenant.Run` 统一入口 + 内容寻址跨项目去重，横向扩租户没有问题。
- **横向扩副本的短板**：限流是**单进程内存**实现（`internal/api/ratelimit.go:11-12` 注释自认），多副本形同虚设；调度并发上限只在 PG 侧函数里（`0018:52-56`），SQLite 无 cap；对象签名 URL TTL 各自硬编码（如 `collab.go:460-461` 1 小时、`editor.go` 15 分钟）。
- **worker 默认并发 2**（`cmd/ppts/worker.go:163`）、进程_step_ 串行，吞吐受限于单进程；长任务与短任务共用队列，缺少按 kind 的隔离队列或优先级。
- **建议**：① 限流改 Redis 或以 DB 为后端（短期至少改成"每副本配额 = 全局/N"并明确文档）；② 按 job kind 引入独立队列与并发配额（narration / export / script / render 分层），避免导出长任务堵住讲稿生成；③ worker 并发、租约、心跳全部 env 可配。

## 5. 易用性 / 可观测 / 可运维

**已有（质量不错）**：`slog` JSON 结构化日志、OTel tracing + `traceprop` 把异步 job 的 span 挂回请求链路（设计很到位）、expvar + 自研 Prometheus 导出、审计 append-only 模型、`docs/runbooks`、回放语料门禁 `internal/validation/replay`、前端 `contrast.mjs` 门禁。

**缺口**
1. `/healthz`（`internal/api/server.go:104-107`）只返回 200 "ok"，**不探活 DB / 对象存储** → 假活。
2. 无 pprof（建议按需开关，避免常开暴露）。

## 8. 把教训变成门禁（最重要的一节）

本次审视最有价值的产出不是清单，而是三条可复制的**判据**：

1. **"编译期不可见"的缺陷必须靠 round-trip 测试兜底。**单靠 review 抓不住列/Scan 顺序错位——我今天写的这个测试，在故意还原错位时立刻报出 `Scan error on column index 10, name "created_at"`，而在此之前同一个包"已经绿了很久"。**每个双存储包都必须有 SQLite 侧往返测试**，这是 Phase 0.5 的全部理由。
2. **"门禁跑绿" ≠ 门禁有效。**`i18n:check` 未进 CI → 39 条孤儿静默积累；`go test` 被 build tag 削掉 107 个用例 → "26 ok" 具有欺骗性。**每个门禁都要有证明它会拦的负测**（就像本次给新测试做的那样）。
3. **"依赖项不可用"永远不能退回成功。**`default → fake` 与 "渲染器缺失继续解析" 是同一种放松：它们都让系统在降级态下输出**和用户不可区分的结果**。凡是兜底，必须同时给开关、告警、产物留痕三件套。
