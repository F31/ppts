# ADR-029：动画与 HTML 成品的六项产品决策

- 状态：已采纳（2026-11-03）
- 关联：`docs/动画视频扩展-设计方案-V1.0.md` §21、`internal/share/`（成品包）、
  `internal/animation/capability.go`（租户策略）、`internal/api/animation_quota.go`（额度）、
  `internal/api/export_bundle.go`（成品导出入口）、`web/src/sharePlayer/`（播放器）

## 背景

方案 §21 留了六项待定，它们不是实现细节，而是**先决定才敢动代码**的产品选择：
先做全片预览会改变编辑器的成本结构；免费层放开导出要同时准备水印与限流；
竖屏要不要进首版决定了版式系统要不要现在就长出第二套栅格。
拖着的代价不是"少一个功能"，而是每个相关提交都要绕开一块说不清的空白。

六项一起拍板，是因为它们互相牵制：竖屏进来会放大免费层的水印面积问题；
文本复制开关的默认值又取决于成品是"交付物"还是"传播物"。

## 决策

| # | 议题 | 决定 | 一句话理由 |
|---|---|---|---|
| ① | 首版是否提供"全片预览" | **不做** | 每页都要渲，成本≈导出；编辑器要的是"这一段对不对"，不是"整片好不好" |
| ② | 免费层是否允许动画导出 | **允许**，限 3 分钟 / 720p，带水印 | 不允许就没有试用入口；限制放在受理时拒绝，不放在渲染后失败 |
| ③ | 竖屏 9:16 是否进首版 | **进** | 竖屏是当前最主要的投放形态，晚做等于把版式系统返工 |
| ④ | 是否投入 Lottie 精修通道 | **暂缓** | 依赖设计资源；现有 transition/clip/camera 已覆盖主要观感，缺口是"更好看"而非"能不能用" |
| ⑤ | HTML 成品默认形态 | **单文件 + 目录包都出** | 单文件便于转发，目录包便于托管与增量更新；两者共用同一份组装 |
| ⑥ | 是否开放文本复制 | **租户级开关，默认关闭** | 可检索/可翻译是 HTML 相对视频的核心优势，也是泄露面；默认值决定它是优势还是事故 |

### ① 全片预览：不做

预览的契约是"≤3s 给一页的结果"（`internal/api/animation_preview.go`）。
全片预览意味着一次编辑动作渲一遍全片：14 页 6 分钟的片子在本机实测 2m33s，
这个等待放进编辑器就等于"每改一句台词等两分半"。

替代方案已经够用：**逐页预览 + 时长条**。用户要判断的是"第 4 段开始时这行字出现了吗"，
这个问题只需要一页 + 一段时间。真要看整片就导出——那时等待有明确预期（进度条 + 任务列表）。

重估条件：渲染吞吐提升到 ≥3× 实时，或预览改为"只渲改变点附近的时间窗"。

### ② 免费层：允许，但限时长、限分辨率、带水印

三个限制各自的职责不同，不能合并成一个"免费版功能少"的模糊说法：

- **时长 3 分钟**：卡住成本的大头。渲染成本随时长线性增长，而 3 分钟足够讲完一件事。
- **720p**：卡住峰值内存与编码时间，同时不牺牲"能看清"这个底线。
- **水印**：不是防盗，是**标明出处**。免费用户的成品会流向各种群聊，
  水印让"这是用 X 做的"随内容一起传播，这是获客路径而不是惩罚。

关键在**受理时拒绝**：超限必须在提交导出时返回明确错误（上限多少、当前多少），
不能先建任务再在 worker 里失败——那正是设计 §7.5 禁止的"静默排队"。

### ③ 竖屏 9:16：进首版

版式系统已按画布百分比落位，主要成本不在几何而在**两套栅格与用例**。
晚做的代价更大：等模板都按 16:9 写死之后再长第二套，等于把已验收的版式全部重排。

真正要修的是**导出侧的默认值**：两个入口都把画布写死 1920×1080（Connect 入口直接写在
快照里，REST 入口缺省时补），而客户端从来不传尺寸——它手里根本没有页尺寸。
竖屏源照此导出，HTML 成品被摆进 16:9 的舞台，MP4 通路则在 render 编译时因比例不符
直接失败（`ErrAspectMismatch`），同一个功能表现为"变形"和"报错"两种症状。

播放器本身没有这个问题：`stage.style.aspectRatio` 一直取自清单的 `video` 字段
（实测 9:16 包得到 0.563），`player.css` 里的 `16 / 9` 只是节点建出来之前的兜底。
初稿把这条写成"播放器写死比例"，是只看了 CSS 没看 JS 的结论——此处更正。

### ④ Lottie：暂缓

不投入的理由只有一个：**没有设计资源**。Lottie 的价值在"设计师做的曲线级动效"，
没有设计师时引入它，产出的是程序生成的、比现有 catalog 更难看的关键帧。
重估条件：有设计师能产出 .json 资源，且有 ≥2 个页型需要它。

### ⑤ HTML 成品：两种形态都出

| 形态 | 适合 | 代价 |
|---|---|---|
| 目录包（zip，现为 `html_bundle`） | 托管、更新、体积敏感 | 需解压；转发时对方要会解压 |
| 单文件（`.html`） | 微信/邮件转发、双击即看 | 体积 = 解压后字节 × 1.33（base64），而 zip 是**压缩后**的；静音夹具实测 36 倍，真实语音待实测（PCM 压缩率低，预期 1.3–1.5 倍） |

两者**必须共用同一份组装**（`buildInto`），否则"目录包能播、单文件不能"这类差异
只会在客户手里被发现。单文件不做独立实现，只做"把同一批条目内联"这一步。

### ⑥ 文本复制：租户级开关，默认关闭

HTML 相对视频的核心优势是**可检索、可复制、可翻译**；同时它也是泄露面——
一份带全文的 HTML 被转发出去，等于把讲稿原文交出去。

默认关闭不是保守，而是把"默认安全"放在"默认方便"之前：企业客户的第一反应
通常是"这东西会不会把我的内容带出去"，而个人创作者想要 Ctrl+F 自己会去开。

开关在**导出时固化**进产物（写进清单），不随租户策略事后翻转：
一份已经发出去的文件，其行为不该因为后台改配置而变化。

## 判据

1. **①** 预览端点的契约不变（1 页、≤3s、超时给明确错误）；不存在"提交整片"的入口。
2. **②** 超限请求在受理时返回带数字的错误（上限/已用/恢复时间），不产生任务；水印在
   成片与 HTML 成品上都可见；限制生效不依赖客户端配合。
3. **③** 同一份竖屏源（9:16）能端到端产出：预览、动画编译、MP4、HTML 成品；
   播放器舞台比例取自清单，改比例不需要改 CSS。
4. **④** 不新增 Lottie 依赖；catalog 里不出现"仅 Lottie 可用"的动效。
5. **⑤** 单文件与目录包从**同一次组装**产出，条目集合一致（单文件是内联视图，不是另一套）；
   单文件通过 V14 自包含门禁（无外链）。
6. **⑥** 关闭时成品内不含可选中文本（页面为纯位图）；开启时文本层内容与页面文字一致，
   且开关状态写进清单，事后不可翻。

## 被否掉的备选

- **① 做"低清全片预览"（480p/10fps）**：省的是像素不是时间，渲染仍需逐页编译与编码，
  等待下降有限，却要多一套画质档位与对应的门禁。
- **② 免费层完全不给动画**：获客成本最低，但用户看不到"动起来是什么样"，
  转化路径断在最关键的一步。
- **② 用"渲染后打水印"代替"受理时限制"**：用户等了十分钟才被告知超限，是最差的失败方式。
- **⑤ 只出单文件**：大 deck（100+ 页）会变成 100MB 级的单个 HTML，每次更新都要重新传。
- **⑥ 默认开启**：把"内容会不会被带走"的决策替客户做了，而这件事无法事后挽回。
