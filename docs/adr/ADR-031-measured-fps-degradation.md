# ADR-031：实测帧率降级用「2s 窗口 × 连续 2 窗」，且只拆动画层

- 状态：已实现（2026-11-08）
- 关联：`web/src/sharePlayer/fps.ts`（帧率计与判据）、`web/src/sharePlayer/main.ts`（接线）、
  `web/player-fps-check.mjs`（纯函数 + 接线门禁）、`scripts/review/bundle-probe.mjs`（`lowfps` 模式）、
  `scripts/review/bundle-gate.py`（V17 两条判据）、`openspec/specs/html-share-quality/spec.md`

## 背景

设计 §20.10 的降级矩阵有两条触发条件：`deviceMemory < 4` **或** 实测 fps < 24。
第一条早已实现（`lowPower`），第二条一直空着。

这不是可以省的项：`navigator.deviceMemory` 只有 Chromium 系提供，且它回答的是
「这台机器有多少内存」。一台 8GB、但核显孱弱或同时开着会议与 IDE 的机器照样报 8，
而 30fps 的合成层动画在它上面会掉到 10–15fps——用户看到的是「视频卡了」，
不会想到「该降级」；播放器自己也不说，于是这条路径永远不会被发现。

## 决策

**在渲染循环里实测帧率，连续两个 2s 窗口低于 24fps 就退成「静态页 + 音频 + 字幕」，单向不回退。**

### 判据

| 参数 | 取值 | 理由 |
|---|---|---|
| 统计窗口 | 2000ms | ≈60 帧，抹平单帧抖动；又不会让「卡了 5 秒」迟迟不降 |
| 降级阈值 | 24fps | 与设计 §20.10 一致；24 本身不降，23.9 才降（判据可核对，不含糊） |
| 迟滞 | 连续 2 个窗口 | 首屏解码、切页重建层都会造成一两个长帧；按单窗判会把正常机器也降级 |
| 长间隔 | > 250ms 视为「被打断」 | 切后台 rAF 直接停、锁屏、断点、长 GC 都是**没在渲染**，不是**渲染得慢**；按 fps 算会得到 0.01，处置完全不同 |
| 方向 | 单向 | 中途恢复动效会让画面突然「开始动」，比一直不动更像故障 |

### 为什么只拆动画层，不动镜头

「等同有声幻灯」的实质是**去掉合成层动画**。页内镜头的成本是换一张已经解码好的图
（`<img>` 的 `src`，按 `dataset.shot` 去重），与页面本身同量级；而元素层是 `WAAPI` 动画 +
每层一张图，才是掉帧的主因。降级后 `pickStageLayers(..., lowPower || degraded)` 与低内存
共用同一条路径：元素层一个不放，矩形焦点遮罩仍保留（那是内容，不是装饰）。

### 为什么采样放在 `render` 之后

`tick` 里 `render(us)` 才是这一帧的成本。先采样再 render，统计到的是「上一帧到这一帧之间
浏览器愿不愿意给帧」，而这一帧本身最贵的部分（重建层、换图）被算到了下一个窗口里。

## 判据的可执行性

- 纯函数（`FpsMeter` / `nextFpsStreak` / `shouldDegradeFps`）在 node 里直接跑，
  时间戳是参数，不读时钟，因此窗口边界、长间隔重置、迟滞都能确定性地测。
- 端到端：`bundle-probe.mjs --mode lowfps` 把 `requestAnimationFrame` 拖到 ~8fps
  （保留 `cancel` 语义，否则暂停后循环还在跑，测到的不是真实行为），
  门禁判据是**「曾经建过层 → 现在为 0」**。只断言最终层数为 0 是不够的：
  页面本来就没有层时，那条断言永远绿。

## 被否掉的方案

- **按单帧判**：一次 GC 就降级，且不可逆。误判代价是这个人再也看不到动效。
- **滑动平均**：迟滞的边界说不清。连续计数「一票否决」更直观，也更好测。
- **降级后连字幕一起停**：那不是降级，是坏掉。字幕与音频是这份产物的下限。
- **用 CSS `will-change` / 减少层图数量等「优化」代替降级**：这些是构建期的取舍，
  与「这台机器此刻跑不动」无关；两者可以并存，但不能互相替代。
