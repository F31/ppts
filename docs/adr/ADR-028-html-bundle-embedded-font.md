# ADR-028：HTML 成品包内嵌字体用「渲染服务二次子集」，按片中字符裁剪

- 状态：已采纳（2026-11-02）
- 关联：`internal/render/fonts.go`（端点与子集器）、`deploy/renderer/subset-runtime.py`（运行期脚本）、
  `internal/share/fontembed.go` / `fontverify.go`（落包与覆盖率校验）、`internal/fonts/coverage.go`（cmap 解析）、
  `deploy/renderer/Dockerfile`、`web/src/sharePlayer/main.ts`（图标改 SVG）

## 背景

方案 §20.6 的 V15 要求「体积预算达标；字体子集覆盖率 100%（片中字符 ⊆ 子集）」，
但实现一直停在 `not_applicable`：`manifest.go` 写着「不内嵌字体，M6-4 再说」，
`bundle-gate.py` 把这一项硬编码为通过。

这不是可以继续拖的项。**成品包里的字幕是 DOM 文本**（逐字高亮要按字符切 span），
它会用打开者机器上的字体渲染；页面内容（PNG 快照）却与字体无关。于是缺字只在字幕上出现、
只在一部分机器上出现，而任何「看起来正常」的人工检查都发现不了。

实测三组数字（Noto Sans CJK SC，CFF 轮廓）：

| 字集 | OTF 体积 | 打进 zip（Deflate）后 |
|---|---|---|
| 全 URO 母版（20976 码位） | 11.1 MB | 约 11 MB |
| 一份 3 页讲稿的实际字符（169 个） | 95 KB | 87 KB |
| 同上转 woff2 | 67 KB | 67 KB |

## 决策

**成品包内嵌的字体由渲染服务在打包时按「该份包实际用到的字符」二次子集产出。**

数据流：

```text
构建期（镜像）：源 TTC 19MB ──charset.txt──▶ 母版 OTF 11MB（全 URO），装进镜像
运行期（打包）：母版 + 片中字符 ──/v1/fonts/subset──▶ 约 90KB 字体，写进 zip
校验期（门禁）：zip 内字体 cmap × 包内文本（标题+VTT+app.js）──▶ 覆盖率
```

## 判据

### 1. 为什么按片中字符裁，而不是内嵌母版

差三个数量级：11.1 MB 与 87 KB。方案给的 40–90 KB 目标正是按片中字符裁的结果。
内嵌母版等于把「一个字体库」塞进「一份讲稿的成品」，而且 11 MB 直接撑爆体积预算。

### 2. 为什么放在渲染服务，而不是主仓库自研或新起 sidecar

CFF 轮廓的子集化没有可用的纯 Go 实现；`fontTools` 是唯一成熟工具。它已经在镜像里了
（构建期裁母版用），差别只是要不要把它留在运行镜像。

- **自研 Go 子集器**：要处理 CFF INDEX、charstrings、subrs、charset、FDSelect，
  风险与验证成本远高于这个功能的收益。否决。
- **新起一个只做字体的 sidecar**：多一个部署单元、一套健康检查、一套告警、一份 compose，
  换来「渲染镜像不加 15 MB」。为一个裁剪功能付这份运维税不划算。否决。
- **放进渲染服务**：镜像 `+15 MB`（`python3-fonttools`），复用它已有的母版字体与部署。
  采纳。

这条与 ADR-15 的关系要说清：ADR-15 否决的是「用构建期子集替代全量字体」这个做法，
理由是**渲染路径根本不读字体**（合成器只有 `<Img>`）。它没有禁止镜像里出现解释器。
本 ADR 新增的用途（HTML 包内嵌）与渲染路径无关，因此不构成对 ADR-15 的推翻。

### 3. 为什么是「二次子集」而不是直接读源 TTC

源 TTC 19 MB，母版 11 MB，二次子集省 8 MB。更重要的是一致性：母版本身就是
`charset.txt` 的产物，从它裁出来的字体**天然继承同一个覆盖边界**——母版没有的字
（CJK Ext-A/B、emoji）会如实报成 `missing`，而不是悄悄从源字体里补上。
「覆盖范围的唯一事实源」因此仍然只有 `charset.txt` 一个。

### 4. 为什么内嵌 OTF 而不是 woff2

woff2 体积只优 12%（87 KB → 67 KB），而它的 cmap 被 Brotli 压在容器里，Go 标准库没有
Brotli——**校验覆盖率就得再引一个解码器**，还要处理「解压失败怎么算」这类分支。

V15 要求独立校验（见下），用 OTF 时 `internal/fonts` 用 150 行解析 cmap 格式 4/12 即可，
零依赖。12% 换掉一个解码依赖与一整类错误分支，划算。

### 5. 为什么播放器图标改成了内联 SVG

做覆盖率校验时才发现：播放器的 `▶ ❚❚ ↻ ‹ ›` 五个字符，**Noto Sans CJK SC 一个都没有**
（它是 Latin+Greek+Cyrillic+CJK，几何图形与箭头只覆盖部分区间）。用字符意味着图标显示
与否取决于打开者装了哪个符号字体——在 Windows 上可能靠 Segoe UI Symbol 侥幸有，
在精简 Linux 上就是方框。

改成 SVG path 后：图标不再依赖任何字体，且 UI 不再向字集里塞生僻字形，
「覆盖率 100%」才是可达的。这个缺陷在引入内嵌字体**之前就存在**，只是没有人测过。

### 6. 门禁必须独立验，不读被测系统的账本

`manifest.fontMissing` 是打包器自己算的。打包器漏收一个文本来源时，它的字集就少几个字，
覆盖率当然「100%」——账本和账一起错。

所以 `share-verify` 从**包内实际文件**重建字集（标题取清单、字幕解析 VTT、播放器文案读
`app.js`），再解析字体 cmap 逐字比对。`fontMissing` 只作为对照信息保留。

代价是两处都要维护「怎么取字幕文本」，所以 `share.SubtitleTexts` 是导出的，
打包与校验共用同一份实现。

## 后果

- 成品包增大约 **87 KB**（占 3 MiB 基数约 3%）。
- 渲染镜像增大 **约 15 MB**（`python3-fonttools`），构建期多一条子集自检（裁不出来就构建失败）。
- 打包多一次 RPC（实测亚秒级），带 20s 超时；渲染服务不可达或未配置时**降级为不内嵌字体**，
  包照常可用——这与引入内嵌字体之前的行为一致。
- `bundle-gate.py` 的 V15 字体项从 `not_applicable` 变为真判据（阻断）。
- 已知边界：`charset.txt` 不收 CJK Ext-A/B，真出现这类生僻字时它们进 `fontMissing`，
  由系统字体回退。这是既定设计，不是本 ADR 的缺口。

## 重估条件

1. **出现第二个需要按字符裁字体的消费者**（例如矢量文字重绘、Lottie 文本图层）：
   那就把子集能力抽成独立服务，而不是让渲染服务兼着做。
2. **字体体积成为体积预算的主要项**（超过 10%）：那时再评估 woff2，并为此引入 Brotli 解码依赖。
3. **播放器需要 Bold**：现在只裁 Regular（约 87 KB）。加 Bold 会让字体体积接近翻倍，
   需要重新核对预算，而不是直接加。
