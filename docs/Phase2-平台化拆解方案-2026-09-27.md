## 0. 先更正一处：Phase 2 不是"多租户计费 / 开放 API / 插件化 TTS"

上一轮我在回复中把 Phase 2 描述为"多租户计费、开放 API、插件化 TTS 等方向"——**这是我自己推测的，与文档不符**。文档 §7 的 Phase 2 原文是四项：

1. 前端工程化（`api.ts` 按域拆分、公共组件抽取、`ProjectEditor` 拆分、轮询统一）
2. 契约自动化（`buf.gen.yaml` 增 TS 插件，**或**退而做"后端 JSON tag ↔ 前端类型"结构快照测试）
3. 可观测与运维（`/healthz` 真探活、pprof、Dockerfile 非 root + HEALTHCHECK、`migrate` 加 `pg_advisory_lock`、SLO/告警与 `docs/runbooks` 对齐）
4. 可扩展性（按 job kind 的独立队列与并发配额；限流改分布式；审计覆盖删除/导出/公开发布/匿名分享访问）

**这四项都是"工程与运维成熟度"，不含新业务能力。** 如果需要计费/开放 API/插件化 TTS，那是另一个独立议题（可另立 Phase 3），不在这份拆解范围内——请先确认你想要的是哪个。

## 2. 拆解与排序建议

排序原则沿用 Phase 1 的判据：**先修真缺陷，再做整洁，最后做前提不成立需要换路线的**。

### P2-A　可观测与运维（建议最先做）

> 理由：含两个**真缺陷**（假探活、限流多副本失效中的探活部分）+ 两项运维硬要求（非 root、迁移锁）。工作量最小、可独立交付、无需改业务语义。

| # | 任务 | 验收判据 |
|---|---|---|
| A1 | `/healthz` 真探活：DB `Ping` + 对象存可达性；失败返回 503 且带分项原因 | **反向验证**：注入 DB 不可达 → 必须 503（当前恒 200）。`/healthz` 仍须免鉴权、不得泄漏内部细节（只报分项 up/down） |
| A2 | `Dockerfile.api` / `Dockerfile.worker` 加非 root `USER` + `HEALTHCHECK` | 容器内 `id` 非 root；`HEALTHCHECK` 指向 `/healthz` |
| A3 | `migrate` 加 `pg_advisory_lock`，并显式区分"抢到锁执行"与"等待锁后跳过" | 两进程并发 migrate → 只有一个真正执行；SQLite profile 下**不得**因此失败（本机可真跑验证） |
| A4 | 按需 pprof：默认**不挂载**，由显式开关启用且复用既有 token 校验 | 承 Phase 0.4 `/debug/vars` 的 fail-closed 判据：未配 token 一律拒绝，不得裸挂 |
| A5 | SLO/告警规则与 `docs/runbooks/` 对齐 | 每条告警在 runbook 有对应处置步骤；runbook 里每条处置步骤能指回告警名（双向可核对） |

### P2-B　可扩展性

| # | 任务 | 验收判据 |
|---|---|---|
| B1 | 限流改分布式后端（基于 PG/Redis），保留进程内实现作单副本降级 | **反向验证**：两个 limiter 实例共享同一计数（现有实现下必然各自放行 → 测试变红）。降级路径须给开关 + 告警（承 A26：降级不得与正常态外观相同） |
| B2 | 审计覆盖盘点：删除 / 导出 / 公开发布 / **匿名分享访问** 四类，缺哪类补哪类 | 先出覆盖矩阵（实测而非看代码猜）；匿名分享审计注意**不得记录可反推分享链接的信息** |
| B3 | 按 job kind 的独立队列与并发配额 | 先量现状（各 kind 的排队时长分布）再定配额；无数据则先只做**可观测**（按 kind 打点），配额留到有数据后再配。**不要凭直觉设数字** |

> B3 的风险提示：`ClaimNext` 走 `ppts_claim_next_job` 调度函数，改按 kind 分发需重建该函数（同 Phase 1.1 的教训：改列清单要同步重建依赖它的函数）。建议先做可观测，确认真的存在饥饿再动调度。

### P2-C　前端工程化（工作量最大）

| # | 任务 | 验收判据 |
|---|---|---|
| C1 | 抽 `core.ts`：默认 15s 超时、GET 退避重试，集中到一处 | 承 Phase 1.5a：只允许 `api.ts`/`auth.ts` 发请求，`api-contract-check.mjs` 必须仍绿 |
| C2 | `api.ts` 按域拆分 `api/{projects,scripts,narration,jobs,tenant,export,public}.ts` | 拆分**只动文件边界不动契约**；分域后 `api:check` 规则需同步（当前规则限定只能 api.ts/auth.ts 发请求） |
| C3 | 抽公共组件 `<AsyncState>`/`<LoadFailure>`/`<EmptyState>`/`<Pager>`/`<Modal>` | 承 A26：**空态与失败态必须是两个状态**，抽取过程中不得把失败压成空态 |
| C4 | 统一轮询 hook（约 20 行）替代 12 处裸 `setInterval` | 12 处改为同一 hook；hook 必须处理**页面隐藏时暂停**与**错误退避**（现有裸轮询多半两者都缺，这是真缺陷不只是整洁） |
| C5 | `ProjectEditor.tsx` 2097 → ≤1200 行 | 建议在 C3/C4 之后做：公共组件与轮询抽走后行数自然下降，**先拆会白拆** |

### P2-D　契约自动化（需先定路线）

**文档给的路线 A（`buf.gen.yaml` 增 TS 插件）前提不成立**：`buf`/`protoc` 不可用是项目既定约束（Phase 1 起所有新后端能力都走原生 HTTP，不改 proto）。强行引入等于新增一条无人能本地执行的生成链路。

建议走**路线 B（结构快照测试）**，但要先界定它的能力边界：

- 能做：后端 handler 的 JSON tag ↔ 前端类型字段**一致性**快照（缺字段/改名 → CI 红）
- 做不了：类型自动同步（前端类型仍手写）

| # | 任务 | 验收判据 |
|---|---|---|
| D1 | 选一处试点（建议 `jobs` 域：字段多、双写已分诊）做结构快照测试 | **反向验证**：故意删一个后端 JSON tag 或改前端字段名 → 测试变红 |
| D2 | 试点通过后再决定是否推广到全部 7 个域 | 若试点显示"每次改字段都要手动改两处"，说明收益不抵成本，应停在试点 |

> 诚实标注：路线 B 的收益是**防漏改**，不是**省事**。别把它包装成"类型自动同步"。

## 3. 排序建议（供你裁定）

```
P2-A 可观测与运维   ← 真缺陷 + 工作量小，建议最先
P2-B 可扩展性       ← 限流是真缺陷；B3 建议先只做可观测
P2-C 前端工程化     ← 工作量最大，建议 A/B 之后
P2-D 契约自动化     ← 前提不成立需换路线，建议先试点
```

若只想挑一部分做，**我的建议是 A + B1 + B2 + C4**：这四个都指向真缺陷（假探活、限流多副本失效、审计盲区、轮询无退避），其余偏整洁。

## 4. 沿用 Phase 1 的三条判据（每项都必须满足）

1. **动手前先核实现状，不照单施工。** Phase 1 有两条计划项按字面实现是错的（"显式 Release"早已被 `lease_owner=NULL` 覆盖；"孤儿扫描"因 `projects` 只有软删除、全仓无 `DELETE FROM jobs` 而永不触发）。P2-B3 尤其需要先量数据。
2. **门禁跑绿 ≠ 门禁有效，必须有反向验证。** Phase 1.5 的路由门禁第一版跑绿但注入后不拦（`spa` 组 prefix `"/"` 前缀匹配恒真，吸收了所有未登记路由）。本方案 A1/B1/D1 均已写明反向验证判据。
3. **清单必须自动提取。** 手写清单两周漂移 12 条（96 → 108）。B2 的审计覆盖矩阵也应由代码提取而非手写。

另：每个里程碑 = 一次 commit + push，推送后核实 `git rev-list --left-right --count origin/main...HEAD` = `0 0`；提交前 `git status --short` 复查并发写者（本仓库长期有他人在途改动，只 `git add` 自己的文件）。

## 7. Phase 3 — 商业化能力拆解

> 本文 §1 的实测方法对 Phase 3 同样适用——**动手前先核实现有成熟度**。
> 实测发现：三项里**只有一项是真正"从零建"**，另两项已有相当扎实的基础，
> 照字面当成新功能做会重复建轮子。

### 实测现状（关键：与我们通常以为的不同）

| 方向 | 实测 | 真实缺口 |
|---|---|---|
| **T3-C 插件化 TTS** | `internal/integrations/tts/tts.go:25` 已有 `TTSProvider` 接口，**只有 2 个方法**（`Capabilities` + `Synthesize`）；现有实现 `siliconflow.go`、`fake.go` | **已经有插件化了**，只是**编译期选 provider**（在包内 switch），缺的是"外部注册/发现"：运行时注册表 + 按配置装配 + 第三方实现的加载约定 |
| **T3-A 计费** | `internal/usage/` 已实现**额度预占、结算、账本、成本记录**（V4.0 §4.2/§12.2）；计量口径有 `gen_seconds`、`llm_tokens`；供应商成本与用户计费**分开记录**；被 6 个包调用 | **计量层已齐**。缺的是"把计量变成账单"：套餐/额度档位、周期结算、账单导出、欠费拦截策略 |
| **T3-B 开放 API** | `internal/gateway/` **不是**对外开放 API——它是**模型网关配置管理**（TTS/LLM 的 API key 加密存储 + 平台默认行兜底 + 30s TTL 缓存） | **真正的开放 API 是零基础**：无 API key 签发、无 scope、无按 key 配额、无文档 |

> ⚠️ 注意 T3-B 的命名陷阱：`gateway` 包名字像"API 网关"，实际是"模型服务商网关配置"。
> 如果按字面理解成"已有网关，加个鉴权就行"，会做出完全错误的估算。

### P3-A　计费（依赖 P2-B 的配额底座）

| # | 任务 | 验收判据 |
|---|---|---|
| A1 | 套餐/额度档位：`usage` 现有的是"按次预占-结算"，需加**周期额度**概念（月度重置） | 周期边界由**时钟注入**决定（不得直接调 `time.Now()`，否则无法测试月切）；**先核实**现有的 `Kind` 够不够表达再决定是否加表，别先建新表 |
| A2 | 账单：按租户+周期聚合 `ledger` 产出账单 | 与 `usage` 现有账本口径一致；**结算动作幂等**（重复跑不重复出账） |
| A3 | 欠费拦截策略：超额时拒绝还是降级 | 承 A26：**不允许静默降级**。必须先有明确的用户提示与告警，再谈拦截；默认策略建议 fail-closed（明确报错，拒绝执行） |

### P3-B　开放 API（工作量最大，建议最后做）

| # | 任务 | 验收判据 |
|---|---|---|
| B1 | API key 签发与存储：哈希存储、**明文仅签发时返回一次** | 与现有 `/debug/vars` fail-closed 同源：不得在任何日志/审计里落成明文 |
| B2 | scope 粒度 + 按 key 配额/限流 | 复用 P2-B1 的分布式限流（这是 P3-B 排在 P2-B 之后的原因） |
| B3 | 对外文档与版本策略 | 承 Phase 1.5 教训：**列出后必须指定负责人**，否则会腐烂成"看着像在用、实际没人管"的死路由 |

### P3-C　插件化 TTS（建议最先做——已有 80% 基础）

| # | 任务 | 验收判据 |
|---|---|---|
| C1 | provider 运行时注册表：把编译期 switch 换成注册表 | 承 Phase 1.4 的做法——注册表作**单一来源**，配覆盖测试（新增 provider 未登记 → 测试失败） |
| C2 | 第三方实现加载约定（接口 + 能力声明 + 配置 schema） | `TTSProvider` 只有 2 个方法，这是**刻意的窄接口**，扩展时不要加方法而是加可选能力接口 |
| C3 | 能力协商已在 `Capabilities` 里，补齐"不支持时的行为" | 承 A26：不支持必须明确报错，**不得静默丢弃参数**（注释里已写明这条约定，需落成测试而非停留在注释） |

### Phase 3 排序建议

```
P3-C 插件化 TTS   ← 已有 TTSProvider 窄接口，落地最快，先做能立刻验证注册机制是否够用
P3-A 计费         ← 计量层已齐，主要缺口是账单与拦截策略
P3-B 开放 API     ← 真正从零开始 + 依赖 P2-B 限流底座，最后做
```

理论上 Phase 2 全部完成后才开始 Phase 3。若想提前做 P3-C，它**不依赖** Phase 2 任何一项，可以并行。
