# PPT自动讲解工具 — 整体技术方案 V3

> 对比对象：`PPT自动讲解工具-技术方案-V2.md`（V2：Go+go-pptx底座换血）
> V3核心议题：**多端支持（Web/移动App/桌面）+ 高可用 + 多租户运营**。V2解决的是"用什么组件把产品做出来"，V3解决的是"这个产品长成一个能被多个客户端、多个租户同时使用、还扛得住故障的系统时，架构应该长什么样"。
> 设计哲学延续go-pptx方案里已经验证过的一条纪律：**不为"看起来更先进"而引入复杂度，只在真实需求驱动下才升级架构**（呼应go-pptx方案"拒绝运行时微内核"的论证方式）。

---

## 〇、V3 相对 V2 的变更总览

| 维度 | V2 | V3 |
|---|---|---|
| 部署形态 | 单一Go二进制，隐含单实例假设 | **模块化单体（Modular Monolith）起步**，无状态化设计，可水平扩展，未来可平滑拆分为微服务 |
| API层 | 未明确设计，隐含REST | **契约优先**：Protobuf定义 + Connect（同时提供gRPC和REST/JSON），一份契约生成多端客户端 |
| 任务队列 | goroutine worker pool（进程内） | 进程内pool用于**单实例场景**，引入**NATS JetStream**作为可选升级路径应对多实例场景，两者通过同一接口切换 |
| 多端 | 仅Web+简单提及移动 | **Web（Next.js）+ 移动（Flutter）+ 桌面（Wails，直接内嵌go-pptx离线运行）**三端并行方案 |
| 租户模型 | 未涉及 | 共享库+`tenant_id`+**Postgres行级安全（RLS）**双重隔离，配额/计量/RBAC/SSO |
| 可用性 | 未涉及 | 无状态服务水平扩展、分布式任务幂等、熔断限流、可观测性三件套（Trace/Metric/Log） |
| 数据库 | 未提及具体选型 | **PostgreSQL**为主存储，明确选型理由 |

## 一、总体架构原则

### 1.1 模块化单体优先，拒绝过早微服务化

这是V3最重要的一条架构纪律，直接延续go-pptx方案"拒绝运行时微内核"的判断逻辑：**微服务的价值只有在团队规模、独立扩缩容需求、故障隔离需求真实出现时才能兑现，过早拆分只会把网络调用、分布式事务、多套CI/CD这些成本提前引入**，与"轻量敏捷"的要求直接冲突。

V3的选择是：**内部按清晰的领域边界分层解耦（Clean Architecture / 端口与适配器模式），对外仍以少数几个可独立部署的服务单元存在**，具体拆分粒度见1.3节。这样做的好处是：内部模块边界一旦清晰，未来某个模块（比如渲染/合成这类重CPU负载的部分）需要独立扩缩容时，可以**平滑拆分成独立进程**而不需要重写业务逻辑——因为分层已经做好了，拆分只是把某一层从"函数调用"改成"网络调用"。

### 1.2 分层解耦：端口与适配器模式（Ports & Adapters）

```
┌─────────────────────────────────────────────────────────────┐
│  客户端层：Web / 移动App / 桌面App                             │
└───────────────────────────┬─────────────────────────────────┘
                             │ Connect (gRPC + REST/JSON 同源双协议)
┌───────────────────────────▼─────────────────────────────────┐
│  API层（Interface Adapters）                                  │
│  - 契约定义（.proto）→ 生成多端类型安全客户端                    │
│  - 鉴权中间件、租户上下文注入、限流、请求校验                     │
└───────────────────────────┬─────────────────────────────────┘
                             │
┌───────────────────────────▼─────────────────────────────────┐
│  领域/编排层（Application Layer，与框架无关的纯业务逻辑）        │
│  - 讲解任务编排（NarrationPipeline）                           │
│  - 租户/配额/计费领域逻辑                                       │
│  - 讲稿版本管理、审计记录领域逻辑                                │
└───────────────────────────┬─────────────────────────────────┘
                             │ 依赖倒置：领域层定义接口，基础设施层实现
┌───────────────────────────▼─────────────────────────────────┐
│  端口定义（Interfaces）：TTSProvider / AvatarProvider /         │
│  StorageProvider / QueueProvider / IdentityProvider(SSO)      │
└──┬──────────────┬──────────────┬──────────────┬──────────────┘
   │              │              │              │
┌──▼───┐    ┌─────▼─────┐  ┌─────▼─────┐  ┌─────▼─────┐
│go-pptx│    │TTS/数字人  │  │对象存储    │  │Postgres/  │
│核心库 │    │第三方适配   │  │S3/OSS实现  │  │NATS实现   │
└───────┘    └───────────┘  └───────────┘  └───────────┘
```

**这个分层解决的核心问题**：领域层（"怎么编排一次讲解任务""怎么判断租户是否超配额"）完全不知道底层用的是Postgres还是MySQL、是S3还是OSS、是进程内队列还是NATS——这些全部通过接口在最外层注入。这不是抽象癖，而是直接服务于"未来要拆分成微服务/要换供应商/要支持私有化部署对接客户自己的存储"这几个真实可能发生的需求。

### 1.3 服务单元拆分建议（起步阶段）

| 服务单元 | 职责 | 起步阶段部署方式 |
|---|---|---|
| **api-gateway** | 鉴权、租户上下文、请求路由、限流 | 与core-service合并部署（模块化单体） |
| **core-service** | 领域逻辑、任务编排、go-pptx调用、数据库读写 | 无状态，可水平扩展多副本 |
| **worker** | TTS/数字人调用、音视频合成（CPU/IO密集） | 独立进程池，独立扩缩容（这是最先值得独立拆分的部分，因为负载特征与api-gateway/core-service明显不同——长耗时、高CPU/IO，不应该和短请求的API服务混部） |
| **go-pptx** | 核心库，以Go module形式被core-service和桌面客户端直接依赖 | 不是网络服务，是被内嵌调用的库 |

**worker最先独立部署的理由**：API请求（比如"查询任务状态"）应该在毫秒级返回，而TTS生成/视频渲染是秒级到分钟级的任务，两者的资源特征（内存/CPU占用曲线）和扩缩容策略完全不同，混部在一起会导致"渲染任务把CPU吃满，导致简单的查询请求也跟着变慢"这类真实的noisy neighbor问题。这是V3里**唯一建议在起步阶段就物理拆分**的部分，其余模块建议保持模块化单体形态直到有明确的扩缩容或团队边界需求。

## 二、Web框架与API层选型

### 2.1 推荐方案：Protobuf契约 + Connect

**这是V3对"多端支持"问题给出的核心技术答案**：与其为Web写一套REST接口、为移动App再单独适配、为桌面客户端再考虑一遍协议兼容，不如**用一份Protobuf契约定义所有接口，一次性生成Web/移动/桌面三端的类型安全客户端**。

具体选型是 **[Connect](https://connectrpc.com)**（而不是传统gRPC+grpc-web）,理由：
- Connect协议基于标准HTTP/1.1和HTTP/2，浏览器可以直接用`fetch`调用，**不需要传统gRPC-web那套Envoy代理做协议转换**，这对"轻量敏捷"和"简单易用"两条都是直接利好；
- 同一份`.proto`定义，**同时**可以用gRPC协议（内部服务间高性能调用）和REST/JSON协议（给第三方系统集成、给不方便用gRPC的场景）访问，不需要额外维护grpc-gateway的映射配置；
- 官方提供Go/TypeScript/Swift/Kotlin的代码生成，直接覆盖Web（TS）、移动App（Swift/Kotlin原生，或通过TS覆盖RN/Flutter的桥接层）、桌面（Go内嵌调用不经过网络，或TS覆盖Wails的前端部分）。

**HTTP服务器底层**：Connect基于标准`net/http`，可以直接搭配 **chi路由器**（轻量、符合Go标准库习惯、生态成熟但不引入额外的框架"魔法"）处理静态资源、健康检查等非RPC路由；不建议引入Gin/Echo这类自带一整套约定的全功能框架——因为Connect已经解决了API层的核心问题，再叠加一个功能重叠的框架只会增加认知负担，这也是"简单易用"原则在框架选型上的直接体现。

### 2.2 契约优先的开发流程

```
1. 定义/修改 .proto 契约（讲解任务、租户、讲稿等所有领域对象和RPC方法）
2. buf生成 Go服务端桩代码 + TS/Swift/Kotlin客户端代码
3. 服务端实现业务逻辑，客户端直接使用生成的类型安全客户端调用
```

这个流程的价值在于：**Web前端、移动App、桌面App三端永远不会因为"某个字段类型理解不一致"而出bug**，因为它们用的是同一份契约生成的代码，这是多端产品里最常见、最消耗调试时间的一类问题的根治方案。

### 2.3 是否需要BFF（Backend for Frontend）层

**结论：暂不需要独立BFF层**。BFF的价值在于"不同客户端需要的数据形状差异很大，且这个差异逻辑复杂到值得单独维护一层"。当前产品的Web/移动/桌面三端核心业务需求高度一致（管理讲解任务、编辑讲稿、查看进度），字段裁剪这类差异可以通过Protobuf的字段选择/分页参数在同一套API里解决，不需要为每个端各写一层BFF——这也是"轻量敏捷"原则的体现：BFF是有价值的模式，但用在这里是"给还没出现的问题预先建解决方案"，应该等到真实出现"某端需要的数据组合方式复杂到污染核心API"时再引入。

## 三、多端支持具体方案

### 3.1 Web端

沿用V2方案：Next.js + TypeScript，新增Connect生成的TS客户端，讲稿本地编辑预览继续使用go-pptx编译的WASM能力（V2/go-pptx方案已规划）。

### 3.2 移动App

延续此前讨论过的Flutter/React Native权衡（时间轴/波形这类精细交互场景Flutter体验更好），V3补充一点新的判断依据：**由于API层已经是Connect生成的类型安全客户端，两个框架接入后端的成本差异很小**，选型可以更纯粹地按"团队技能栈"和"交互复杂度"决定，不需要再考虑"哪个框架更容易对接后端"这层因素——这也算是契约优先设计带来的一个附加简化。

### 3.3 桌面端：Wails + go-pptx直接内嵌调用（V3的关键创新点）

这是V3在多端支持上最值得强调的一处架构决策。桌面端有两种模式可选：

| 模式 | 说明 | 适用场景 |
|---|---|---|
| **联网模式** | 桌面App像Web一样通过Connect客户端调用远程core-service | 需要数字人生成、云端TTS这类必须依赖服务端能力的场景 |
| **离线优先模式（V3新增）** | 桌面App用**Wails**（Go后端+系统原生WebView前端，不像Electron那样打包完整Chromium，产物体积小很多）打包，**直接把go-pptx作为Go module内嵌进桌面应用**，PPT解析、备注提取、音频嵌入、计时同步这些核心操作完全在用户本机完成，不需要联网、不经过任何服务端 | 对隐私敏感的企业用户（PPT不出本机）、弱网/内网环境、以及"只需要基础配音功�不需要数字人"的轻量场景 |

**为什么这个设计成立、而且成本很低**：go-pptx是纯Go、零cgo的库（这一约束在go-pptx方案里反复强调），这意味着它既可以像go-pptx方案里讨论的那样编译成WASM给Web用，也可以**原生编译进Wails桌面应用直接调用**，同一套核心库覆盖了"浏览器端"和"桌面端"两种完全不同的运行环境，这是选择Rust核心（如office_oxide）或Python（python-pptx）都做不到的一点——Rust需要额外的FFI桥接，Python完全无法用于桌面/浏览器原生打包。

**建议**：桌面端默认给用户"离线基础版"（免费/低成本、无需联网、纯配音），需要数字人/云端高质量TTS时提示切换到"联网增强版"，这个模式选择本身也是一个自然的产品分层/商业化切入点。

## 四、多租户设计

### 4.1 隔离模型：共享库 + tenant_id + Postgres行级安全（RLS）

多租户隔离常见三种模型——独立数据库、独立schema、共享表+租户字段——分别对应"隔离性强但运维成本高"到"运维简单但隔离性弱"的光谱。V3选择**共享表+`tenant_id`字段**作为起步方案，但补充一层容易被忽视的加固手段：**PostgreSQL的行级安全（Row Level Security）**。

```sql
ALTER TABLE narration_tasks ENABLE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON narration_tasks
    USING (tenant_id = current_setting('app.current_tenant')::uuid);
```

这样即便应用层某处代码忘记加`WHERE tenant_id = ?`条件（这是共享表模型下最常见的安全事故来源），数据库引擎本身也会拒绝跨租户读取，是一层**应用层bug之外的纵深防御**，成本只是在每次数据库连接建立时设置一次当前租户上下文，几乎不增加代码复杂度，却大幅降低"租户数据泄露"这类严重事故的概率。

**升级路径**：如果未来出现个别超大型企业客户明确要求数据物理隔离（合规要求），可以为该租户单独切换到独立schema甚至独立数据库实例，架构上只需要在数据访问层的`StorageProvider`接口实现里按租户路由到不同连接，不需要改动上层业务逻辑——这再次体现了1.2节分层解耦的价值。

### 4.2 资源配额与限流：延伸go-pptx的资源预算理念

go-pptx方案里已经为单份文档处理设计了资源预算体系（13章），V3把这个理念**延伸到服务级、租户级**：

```go
type TenantQuota struct {
    MaxConcurrentTasks   int           // 并发任务数上限
    MonthlyTTSMinutes    int           // 每月TTS配音时长额度
    MonthlyAvatarMinutes int           // 每月数字人生成时长额度（成本更高，单独计量）
    StorageQuotaGB       int
    MaxFileSizeMB        int
}
```

配额检查在API层（请求校验）和worker层（任务真正执行前二次校验，防止并发请求绕过API层检查）各做一次，这是分布式系统里"配额检查"这类操作常见的经验教训——只在入口检查一次，在高并发场景下容易被竞态条件绕过。

### 4.3 计量与计费

每个worker任务完成后上报用量事件（TTS时长、数字人分钟数、存储增量）到一个独立的计量服务/表，计费逻辑完全基于这些事件重新计算，不直接修改任务本身的状态字段——这样计费口径的变更（比如未来调整定价策略）不需要改动任务处理逻辑，两者解耦。

### 4.4 RBAC与企业级身份集成（SSO）

参考V2里提到的Synthesia靠SSO/安全能力拿下企业客户这一点，V3把身份认证也做成一个可插拔的`IdentityProvider`接口——默认实现是自建的邮箱/密码认证，企业租户可以配置SAML/OIDC对接客户自己的身份提供商（Okta/Azure AD等），这个接口化设计让"支持企业SSO"这件事不需要在核心业务逻辑里散落大量"if是企业租户走另一套认证逻辑"的分支判断。

## 五、高可用设计

### 5.1 无状态服务 + 水平扩展

core-service和api-gateway都设计为**无状态**——任何用户会话、任务中间状态都不保存在服务进程内存里，而是存在Postgres/Redis/对象存储中。这样任意一个实例故障，负载均衡器可以直接把流量切到其他健康实例，不丢失任何会话或任务状态，也是水平扩展的前提条件。

### 5.2 任务队列：从进程内goroutine pool到分布式队列的升级路径

V2设计的goroutine worker pool在**单实例**场景下工作得很好（呼应go-pptx创新设计里"流水线化生成"的并发思路），但多实例部署后会出现问题：如果任务提交到实例A的内存队列，而实例A故障重启，队列里的任务会直接丢失。

**V3方案**：把任务队列这个"端口"抽象成接口，提供两种实现：

```go
type TaskQueue interface {
    Enqueue(ctx context.Context, task Task) error
    Dequeue(ctx context.Context) (Task, error)
    Ack(ctx context.Context, taskID string) error
}
```

- **进程内实现**：基于channel，适合单实例/开发环境，延续V2设计，零外部依赖；
- **NATS JetStream实现**：适合多实例生产环境，NATS本身是Go编写、部署简单（相比Kafka运维成本低得多），JetStream提供持久化和至少一次投递保证，任务不会因为某个worker实例重启而丢失。

**何时切换**：只有当真实需要多实例部署（用户量增长到单实例扛不住）时才引入NATS，起步阶段用进程内实现完全够用，这再次体现"轻量敏捷"原则——不为尚未出现的规模问题预先引入运维复杂度。

### 5.3 任务幂等性：复用go-pptx的TrackKey理念

go-pptx设计方案里为音轨绑定设计了`TrackKey`保证"同一个音轨可以被安全地重复处理而不产生重复内容"。V3把这个幂等性理念延伸到整个任务系统——每个讲解任务提交时携带一个幂等键，worker处理前先检查该键是否已经处理过，这样即便因为网络重试、队列消息重复投递导致同一个任务被处理两次，也不会产生重复的音频文件或重复扣费，这是分布式系统里任务队列"至少一次投递"语义必须搭配的标准做法。

### 5.4 第三方依赖故障隔离：熔断与降级

TTS/数字人这类第三方API是整个系统里最不可控的外部依赖。V3要求所有`TTSProvider`/`AvatarProvider`的实现都包裹一层熔断器（如`sony/gobreaker`这类成熟的Go熔断库）——当某个供应商连续失败达到阈值，自动短路请求并快速失败，避免worker因为反复等待一个已经不可用的第三方API超时而堆积任务，同时触发告警让运维介入，必要时自动降级切换到备用供应商（这也是V2里"多引擎适配层"设计从一开始就要坚持的原因——它不只是成本优化的手段，也是高可用的手段）。

### 5.5 可观测性：Trace / Metric / Log 三件套

这是此前go-pptx方案评审里提到过、但当时限定在"组件库"范畴的建议，V3把它提升为整个产品的强制要求：

- **分布式追踪（OpenTelemetry）**：一个讲解任务从API接收、到worker处理、到调用TTS/数字人API、到最终写入存储，全链路用一个trace ID串联，出问题时能直接定位是哪个环节慢或失败；
- **指标（Metrics）**：任务队列积压长度、各供应商API的成功率/延迟、租户级配额使用率，这些指标直接驱动告警和容量规划；
- **结构化日志**：所有日志携带`tenant_id`/`task_id`/`trace_id`，方便按租户或按任务排查问题，也是多租户场景下"某个租户投诉问题，需要精确定位到只属于他的日志"这个真实需求的直接支撑。

### 5.6 灾备与多可用区

起步阶段：数据库和对象存储选择支持多可用区自动故障转移的云厂商托管服务（如RDS多AZ、S3天然跨AZ冗余），不需要自己搭建复杂的多活架构；服务实例部署在至少两个可用区，负载均衡器做健康检查自动摘除故障实例。这个阶段的高可用主要靠"选对云服务的高可用选项"而不是自研复杂的多活方案，同样是"轻量敏捷"原则的体现——高可用不等于一开始就要做异地多活。

## 六、可扩展性设计：Provider插件化模式的系统性延伸

V2已经为TTS和数字人设计了`TTSProvider`/`AvatarProvider`可插拔接口，V3把这个"端口与适配器"的纪律系统性地应用到所有外部依赖：

| 端口接口 | 起步实现 | 未来可替换的实现 |
|---|---|---|
| `TTSProvider` | edge-tts | Azure/ElevenLabs/火山引擎 |
| `AvatarProvider` | 空（V2起步阶段可选） | HeyGen/Synthesia/Elai.io |
| `StorageProvider` | S3兼容对象存储 | 阿里云OSS/腾讯云COS/客户私有化存储 |
| `TaskQueue` | 进程内channel | NATS JetStream |
| `IdentityProvider` | 自建邮箱密码 | SAML/OIDC企业SSO |
| `NotificationProvider` | 邮件 | 短信/站内信/Webhook |

**统一纪律**：任何新增外部依赖，第一步永远是先定义接口再实现，业务逻辑只依赖接口。这不是为了抽象而抽象——每一行都对应一个"未来大概率会发生"的真实替换需求（换供应商降成本、企业客户要求私有化存储、引入新的通知渠道），提前留好接口的成本几乎为零，但省去了未来"这段代码里散落着到处调用某个具体SDK"式的痛苦重构。

## 七、可维护性设计

### 7.1 代码组织：Go Module的模块化单体结构

```
repo/
├── proto/                  # 契约定义，独立版本化
├── go-pptx/                 # 核心库，独立module，可被桌面端和核心服务分别依赖
├── internal/
│   ├── domain/               # 领域层：任务编排、租户、配额（不依赖任何框架）
│   ├── ports/                # 接口定义（TTSProvider等）
│   ├── adapters/              # 端口的具体实现
│   │   ├── tts/{edgetts,azure,elevenlabs}/
│   │   ├── avatar/{heygen,synthesia}/
│   │   ├── storage/{s3,oss}/
│   │   └── queue/{inmemory,nats}/
│   ├── api/                   # Connect服务实现，胶合层
│   └── worker/                 # worker主循环
├── cmd/
│   ├── core-service/
│   └── worker/
└── web/, mobile/, desktop/    # 各端客户端代码（或独立仓库）
```

`domain`层是全仓库唯一"不能import任何具体技术选型包"的地方，这条规则由CI静态检查强制（比如用`go vet`自定义规则或`depguard`工具），保证领域逻辑始终可以脱离具体基础设施单独做单元测试，这是"可维护性"最实在的度量标准之一——领域逻辑的单元测试不需要启动数据库、不需要真实调用TTS API。

### 7.2 API版本化

Protobuf天然支持字段级别的向后兼容演进（新增字段不破坏旧客户端），但涉及不兼容变更（删除/重命名字段、改变语义）时，采用显式版本化包路径（如`narration.v1`/`narration.v2`），旧版本在明确的废弃周期后下线，多端客户端可以按自己的升级节奏迁移，不需要被迫和后端同步升级。

## 八、轻量敏捷落地路径：部署拓扑的三个阶段

| 阶段 | 部署拓扑 | 触发升级的信号 |
|---|---|---|
| **阶段一：起步** | 单一Docker Compose：core-service（含api-gateway）+ worker + Postgres + 对象存储，进程内任务队列 | — |
| **阶段二：增长** | core-service多副本水平扩展 + worker独立扩缩容 + 引入NATS JetStream替换进程内队列 + 引入Redis做缓存/限流计数 | 单实例CPU/内存持续高位，或任务队列因单点故障丢失过任务 |
| **阶段三：规模化** | 按1.3节拆分独立服务（如渲染worker与TTS/数字人worker分离，各自按负载特征独立扩缩容）+ 多可用区/异地灾备 + 独立的计量计费服务 | 团队规模扩大到需要多团队独立负责不同模块，或单一worker类型的资源需求出现显著分化 |

**核心纪律**：不预先跳到阶段三。阶段一到阶段二的升级成本很低（因为1.2节的分层解耦已经把这些切换点都做成了接口），阶段二到阶段三才涉及真正的组织和架构复杂度，应该由真实的规模信号驱动，而不是"因为大公司都这么做"。

| 层级 | V2 | V3新增/变更 |

## 十、路线图衔接

V3的多租户/高可用能力建议排在V2产品路线图的"阶段六：企业信任模块"前后并行推进，具体触发时机遵循第八章的三阶段升级信号，不建议在MVP阶段就引入NATS/多副本部署这类复杂度——MVP阶段的核心任务仍然是V2路线图里"打通核心闭环、验证产品价值"，高可用和多租户是产品验证成功、开始承接真实付费客户之后要认真投入的下一阶段工作。

## 十一、一句话总结

**V3不是推翻V2重来，而是在V2已经确立的"Go原生、可插拔适配层"这条架构基因上，补齐了"多个客户端怎么共用一套后端"（契约优先+Connect）、"多个租户怎么安全共存"（共享库+RLS+配额）、"故障发生时系统怎么不整体瘫痪"（无状态+分布式队列+熔断+可观测性）这三块此前完全没有触及、但产品要走向真正多端和规模化运营时无法回避的能力；同时全程坚持"轻量敏捷"的纪律——用模块化单体和进程内实现作为起步默认值，把复杂的分布式组件都设计成可以在真实规模信号出现后再启用的可插拔升级路径，而不是从第一天就背上不必要的架构负担。**
