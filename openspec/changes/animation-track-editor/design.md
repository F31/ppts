# 设计：轨道编辑与分级开放（M4）

## ADR-1 能力判定是一个纯函数，不是一个「读 env 的中间件」

`AnimationPolicy.Resolve(tenantID, GateConfig) Capability` 没有任何 I/O：策略从哪来、部署闸怎么配，
都由调用方作为入参给进来。这样做的原因不是"好测试"（虽然确实好测），而是**三处入口必须得到同一个答案**。

如果判定放在中间件里、handler 各自读 env，那么「导出选项说可用、写规格返回 404」这种分叉只是时间问题：
三处代码的部署条件不同（worker 没有 HTTP 上下文，本地 profile 与生产读不同的 env），漂移几乎是必然的。

代价是调用方要自己取策略。这一点用 `tenantAnimationGate` 包掉，handler 只看到
`Resolve(ctx, tenantID)`。

## ADR-2 指针字段：`nil` 与 `false` 是两件事

`enabled` / `track_editor` / `preview` 都用 `*bool`。

| 值 | 含义 | 行为 |
|---|---|---|
| `nil` | 没配过 | 走灰度 / 默认 |
| `true` | 显式开（白名单） | 绕过灰度 |
| `false` | 显式关（封禁、欠费） | 压过灰度 |

用零值 `bool` 会把「封禁一个租户」与「该租户还没进灰度」合并成同一种状态。后果很具体：
运营把一个欠费租户设为 `false`，灰度扩到 100% 时它又被打开了——因为代码分不清
「明确关掉」和「没设过」。

`rollout_percent` 同理用 `*int`：`0` 是「本租户不参与灰度」，`nil` 是「用部署级默认」。

## ADR-3 迁移：部署级默认百分比，而不是直接翻转默认值

设计 §10.3 的 `animation.enabled` 默认 `false`。本变更引入 `PPTS_ANIMATION_ROLLOUT`（默认 **100**），
租户未设策略时按这个百分比分桶。

**没有直接翻转默认值的理由**：现网已经有一批 `PPTS_ANIMATION_ENABLED=true` 的部署在给所有租户用动画。
如果升级后未配策略的租户一律变 `false`，这些客户会在同一次发版里失去功能，而运营侧的补救手段
是「给每个租户写一条策略」——在故障窗口内根本来不及。

所以：

- 部署闸 `PPTS_ANIMATION_ENABLED=false` → 全关，这一层语义不变；
- 部署闸开、租户未设 → 按 `PPTS_ANIMATION_ROLLOUT`（默认 100 = 与今天一致）；
- 生产想收口：显式设 `PPTS_ANIMATION_ROLLOUT=0`，再逐个开租户。

翻转默认值是后续一次独立发版，前置条件是「所有活跃租户都有显式策略」。这条不写进代码注释就算没定，
因为它决定了升级当天的线上行为。

## ADR-4 分桶：SHA-256 前 8 字节取模，salt 固定不随批次变

```go
bucket = int(binary.BigEndian.Uint64(sha256(salt + "\x00" + tenantID)[:8]) % 100)
```

- 用 SHA-256 而不是 `hash/fnv`：租户 ID 多为有序短串（`t_000123`），FNV 的低位在短串上分布尚可，
  但它的雪崩性弱于 SHA-256，按 100 取模这种小模数更容易出现可见的聚集。分桶要的是**均匀**，
  不是快——每个租户一次，开销可忽略。
- 加 `\x00` 分隔符：`salt="ab" + tenant="c"` 与 `salt="a" + tenant="bc"` 不能撞。
- **salt 不得随灰度批次改变**。改 salt 等于重新洗牌：已经吃到 5% 的租户可能被踢回未开放状态，
  而它可能已经在用这个功能做交付。灰度的语义是「单调扩大」，不是「每轮抽一批新人」。
  部署文档要把这条写成禁令，而不是参数说明。

## ADR-5 关闭是「入口关闭」，不是「任务中止」

租户被关掉时：

- 写规格 → 404；
- 新的导出 → 不勾动画（静态）；
- **已经在渲染的任务照常完成**，产物照常交付。

设计 §11.5 的原话是「回滚只需关 `animation.enabled`；已产出视频不受影响」。让在途任务失败没有收益：
钱已经花了（渲染分钟数已发生），失败只会让用户重新导一次静态版。所以 worker **不读租户 gate**——
它只看部署级开关。这不是遗漏，是 ADR。

## ADR-6 策略读失败：fail closed，但给出可区分的原因

`GetPolicy` 返回 `ErrTenantNotFound`（本地 SQLite 常见）→ 当成「没配过」，走默认百分比。
其它错误（数据库不可用）→ 判为不可用，`reason="policy_unreadable"`。

为什么不是 fail open：动画是花钱的能力，策略读不到时放开等于在最脆弱的时刻放开成本闸。
为什么要区分 `policy_unreadable`：否则「数据库挂了」会显示成「你的租户没开这个功能」，
排查方向完全错。

## 不做

- 用户级灰度：同一份文档在两个同事那里表现不同，支持成本远高于收益。
- `plan` 表：套餐写成租户策略里的布尔位，运营改一条 jsonb 即可，M4 不引入计费模型。

## ADR-7 额度按账期分行，默认不限（第 2 段）

`internal/usage` 的额度模型是**累计上限**（`tenant_quotas.reserved_units + consumed_units <= limit_units`），
没有周期概念：`consumed_units` 从不重置，只有 `SetLimit` 能改。

设计 §10.3 写的是 `animation.max_minutes = 60/月`。要在"按月"和"原子不超卖"之间同时成立，只有一条路：

```
usage_kind = "animation_minutes:2026-10"
```

把账期编进计量种类，跨月天然是**新行**。`Reserve` 的条件更新仍然发生在单行上，因此并发不超卖；
上月的行留在原处供对账；恢复时间就是下月 1 日 00:00 UTC，可以真的算出来并返回。

否决的替代方案：给 `tenant_quotas` 加 `period` 字段 + 在预占事务外判断"是否跨期需要重置"。
那是事务外的读改写，跨期那一刻并发预占可以双花，而"额度不超卖"正是这个功能存在的理由。

**代价写在这里**：`usage_ledger.usage_kind` 会带账期后缀，跨月聚合必须按前缀匹配（`Kind.Base()`）。
不为动画单独加一列，是因为一列 `period` 与"账期在 Kind 里"是同一份信息，加列等于让两种口径共存。

**默认不限量，而不是 60/月**。这是对设计 §10.3 的刻意偏离：

- 升级当天给所有存量租户加一道 60 分钟/月的硬停，与 ADR-3 拒绝翻转灰度默认值是同一类事故——
  已经有人在用这个功能交付，一次发版就把他们挡住；
- 60 是**运营配置值**（写进部署文档的收口步骤），不是一个应当由代码替运营决定的上限。

上限未配置时 `Reserve` 自动建行（`limit_units=-1`），不覆盖运营手工设过的值。

## ADR-8 预占在受理、结算在 worker、释放在终态

三件事分在三个地方，因为只有各自的现场知道该用多少：

| 动作 | 位置 | 依据 |
|---|---|---|
| 预占 | `POST /api/projects/{id}/exports` | 时间轴总时长（= 即将渲染的时长） |
| 结算 | worker 的 `ExportHandler` | 实际渲了动画的页（排除降级页） |
| 释放 | worker 的取消/失败终态钩子 | 没有任何渲染分钟发生 |

三个具体决定：

1. **超限必须拒在受理**。先建任务再在 worker 里失败，就是设计 §7.5 明令禁止的"静默排队"：
   用户以为在渲染，等十分钟得到一条失败。
2. **降级页不计费**。降级页播的是静态段，没花渲染分钟数。按整片结算等于在渲染服务最不稳的时候按满额收费。
   这条在实现时踩过一次：写成 `av != nil && 降级页跳过` 时，`av == nil`（整体退回静态）
   会把整片时长都算进动画分钟——正是"渲染失败却被满额收费"。由
   `TestSettleAnimationMinutesReleasesHoldWhenFullyStatic` 守住。
3. **只在终态释放**。worker 新增 `OnFailed`（与既有 `OnCanceled` 对称），只在不可重试/重试耗尽的
   失败终态触发；可重试的中间失败不释放。中途释放会让重试成功后结算找不到预占，那笔用量变成无主账。

账期在预占与结算两侧都取**任务创建时间**：月末提交、月初跑完的任务，两边必须指向同一行额度。

## 不做（第 2 段）

- 额度在 UI 上展示"本月剩余分钟"：前端目前只透传 `capabilities.maxMinutes`，剩余量要额外读额度表，
  而它在受理失败时才有意义（429 里已经带齐四个数）。
- 提额入口：走既有 `SetLimit` 管理面，M4 不做自助。留给运营。
- 周期滚动任务：账期在计量种类里，跨月不需要任何后台任务去重置。
