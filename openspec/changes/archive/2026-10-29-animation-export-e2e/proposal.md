# 提案：导出接线与逐页动画编辑（M3）

## 为什么做

M2（`animation-render-mvp`）已经能把规格编译成 IR、起渲染服务、产出逐页 `segment_NNN.mp4`，
本机也出过 5 页样片。但**用户在导出对话框里看不到「动画视频」这个选项**：
`internal/app/export.go` 的 MP4 分支仍然只做静态编码（页面图 → 逐页时长 → 一次 ffmpeg 编译）。

能力已经存在却拿不到，是这一阶段最贵的浪费：渲染服务、编译链、客户端降级信号都付了成本，
收益却是 0。本变更把「已造好的能力」接到用户手上，并按设计 §8.8 的降级矩阵兜住它。

## 目标

1. `FormatMP4` 导出在有动画规格且开关打开时走动画通道：编译 IR → 提交渲染 → 收分段 →
   拼接 + 混音 + 烧字幕 → 与静态版同一套产物登记（snapshotHash / 成品行 / 时长）。
2. **失败必降级**：渲染服务不可达、整片渲染失败 → 回退静态版；单页失败 → 只有该页换静态图。
   任何动画故障都不得让用户拿不到视频（§8.8 的关键原则）。
3. 关闭 `animation.enabled` 时与今天完全一致：静态编码参数、snapshotHash、产物字节都不变。
4. 逐页编辑入口（三级入口的第一级）：选预设 / 调强度 / 逐条要点改触发锚点，单页预览 ≤ 3s。

## 非目标

- 轨道编辑（元素级关键帧、开关、配额、灰度）——M4 `animation-track-editor`。
- 渲染缓存与增量重渲——M5 `animation-render-perf`。
- HTML 成品包的 DOM 关键帧——M6-2 `html-bundle-animation`。
- 全片预览（见下方 Q1 决策）。

## 与既有变更的关系

- 依赖 `animation-render-mvp` 的 IR、渲染服务、HTTP 客户端与降级信号；依赖
  `animation-spec-core` 的规格校验与存储。
- **承接 `animation-render-service-image` 的 3.7**（单页失败只降级该页）：该任务在 M2 里
  无法完成，因为当时没有拼接层，也就不存在「单页」这个可替换单元。拼接层在本变更落地。
- 与 `html-share-bundle-static`（M6-1）无耦合：`html_bundle` 分支不动。

## 平台决策

**Q1（路线图 §5）：首版是否提供「全片预览」→ 否，只做单页预览。**

- 全片预览的成本 = 一次完整渲染，与导出同价，却只换来「看一眼」；在配额与并发都没标定前
  开放，会让预览把导出的容量挤掉。
- 单页预览的成本是一页，且正是用户调参时真正要看的东西。
- 留扩展位：`POST /v1/render` 的 IR 本来就按页组织，将来放开全片预览只是去掉「只提交一页」
  的限制，不动契约。
