# 渲染性能（M5）落地说明

> 变更：`animation-render-perf`。对应里程碑 M5「片段缓存 + 增量重渲 + 页级并行」。
> 这份文档回答四个问题：**缓存的是什么、键为什么带前一页、配置怎么配才达标、代价在哪。**

## 1. 缓存的是什么

缓存的一段是**一页的片段**，也就是 `segment_NNN.mp4` 本身——M2 已经定下的产物单位。

```
plan.json ──按页算键──▶ 命中？ ──是──▶ 直接进产物目录（不渲染、不 staging）
                          │
                          └─否──▶ RenderPages(未命中页) ──▶ 回填缓存（降级页除外）
                                                              │
                                                              └──▶ 拼接（M3，不变）
```

缓存是**渲染服务内部**的事，编排层完全不知道它的存在：

- 键需要渲染器版本、字体集合、CRF/GOP、Chrome 版本——这些只有渲染服务自己拿得到；
- 编排层若把计划拆成子计划再提交，`plan.json` 里就没有前一页了，而转场恰恰画的是前一页的末帧——拆了必然出错。

`ServiceConfig.SegmentCache` 为 nil 时行为与引入缓存前完全一致（每页都渲）。这是刻意的：缓存是加速手段，不是正确性前提。

## 2. 键为什么带前一页

合成器把转场挂在**后一页**上：页首 `transitionMs` 内画的是前一页的末帧（`renderer/src/Timeline.tsx` 的 `PageEntry`）。所以一页的像素不只由它自己决定。

```
        ┌── 第 3 页片段 ──┐
第 2 页 ─┤  ├─ 前 0.4s：第 2 页末帧（fade）
        └── 其余：第 3 页 ─┘
```

后果要认下来：

- **改一页脏两页**（它自己 + 后继那一页）；
- 10 页计划的命中率上限是 `(n-2)/n`，n=10 时 **80%**——这正好是实测值，说明缓存已经吃满了。

前一页只在「本页转场真的生效」时入键（`type != none && durationMs > 0`）。0ms 的转场归一成 nil，否则「durationMs 从 0 改成 0」这种无意义差异会白白让键变化。

### 不进键的字段（逐条有理由）

| 字段 | 为什么不进键 |
|---|---|
| `index` | 页序号。同一页挪个位置，像素没变 |
| `slideId` | 命名。重新导入 PDF 会换 ID |
| `plateImage` / `layer.image` | 派生物，路径随工作目录变。进键则换个目录全部失效 |
| `clipId` | 仅供审计定位 |
| `effect` | 审计用途，不参与渲染 |
| `warnings` | 诊断信息 |

`durationMs` 与 `transition.durationMs` 则**必须**进键——它们直接决定帧数。

规范化用一组**显式的投影结构体**（`segmentPage` / `segmentPrev` / `segmentInput`），而不是「把 Plan 整个序列化再删字段」。以后给 `Page` 加字段，默认是**不进键**；要进键得主动改投影。反过来（默认进键）会让每次加诊断字段都全量失效。

## 3. 配置怎么配才达标

设计 §9.6 的三条判据与实测（10 页 / 30 秒 / 1080p30，4 vCPU）：

| 判据 | 目标 | 实测 | 结论 |
|---|---|---|---|
| 二次渲染 | ≤ 10s | **2.4s**（渲染 0.4 + 拼接 2.0） | PASS |
| 改一页命中率 | ≥ 70% | **8/10 = 80%** | PASS（已是理论上限） |
| 30s 正片 P95 | ≤ 120s | 2 位 **133.9s** / 4 位 `2×2` **71.6s** / 4 位 `4×1` **49.3s** | 只有 4 位才 PASS |

**默认的 2 个渲染位达不到 120s。** 这是本次最需要说清的一条：

```
-concurrency 1 -page-concurrency 4   →  1 任务 × 4 页 × 1 帧 = 4 位   P95 49.3s  ← 推荐
-concurrency 2 -page-concurrency 2   →  2 任务 × 2 页 × 2 帧 = 4 位   P95 71.6s
（默认）                              →  2 任务 × 1 页 × 2 帧 = 2 位   P95 133.9s
```

同样是 4 个渲染位，**「4 页 × 1 帧」比「2 页 × 2 帧」快 30%**。原因不难理解：帧级并行在页边界处有同步与产物合并开销，而页级并行的每一页都是一个独立的浏览器上下文与一次独立的编码，收尾时才汇合。

默认值没有改成 4：4 位是 4 个 Chrome + 4 份帧缓冲，在 2 核边端会 OOM。默认值取决于部署形态，留给 M4 的配额/灰度一起定；现在靠部署文档给达标配置（`deploy/renderer/README.md`、`compose.yml`）。

## 4. 代价与踩到的坑

### 磁盘

- 布局 `root/<key[:2]>/<key>.mp4`，前两位当分片目录，避免单目录几万个文件。
- 上限默认 4 GiB（`-segment-cache-max-bytes`），`Put` 时按 mtime 淘汰到 **90%**，不删本次刚写入的项。
- 目录**必须在持久卷上**（ADR-9）。放在容器临时层里，重启即全冷，等于没做缓存。

### 三个坑

1. **环境串不能用 `k=v;` 拼**。`Encoding` 自身就是 `crf=18;gop=30`，拼出来的字符串会撞键。改成 `json.Marshal` 三元数组，由 `TestSegmentEnvStringIsUnambiguous` 锁住。

2. **Windows 上 `rename` 会争用**。多副本同键并发 `Put` 时报 `Access is denied`（Linux 复现不出来）。做法是重试 + 「目标已是非空文件即成功」——同键必然同像素，谁先落地都对。由 `TestDirSegmentCacheConcurrentPutIsAtomic` 抓到。

3. **降级页不能写缓存**。静态替代帧结构上是合法 MP4，写进去就把「这一页当时渲挂了」固化成「这一页永远不动」。`page_render_failed` / `page_skipped` 一律不入缓存。

### 缓存没有能力让渲染失败

- `Get` 出错 → 按未命中，重渲；
- `Put` 出错 → 只记日志，不影响终态；
- 复用前过 `verifyMP4`（存在、≥1 KiB、第 4–8 字节为 `ftyp`），不过就当未命中并替换。

这条性质有对应用例：缓存目录只读时任务仍然 `succeeded`，只是多几行写失败日志；缓存项被截断成 10 字节时该页重渲。

### 一处分析发现、门禁没抓到的缺陷

第一版只给「未命中页」做 staging（复制底图、生成底板与层图）。漏了：**转场页还需要前一页的底板**，否则转场段会退回整页底图——带出场动画时就是旧画面，而且**没有任何 warning**。

修法是 staging 集合取「未命中页 ∪ 其转场依赖的前一页」（`withTransitionPrevs`），并且补了两道防线：

- `TestStagePagesIncludesTransitionPredecessor`：结构用例，断言集合成员；
- `edit-parity` 场景：端到端比对成片。

要说明的是：这个缺陷是**读合成器代码时发现的，不是门禁抓到的**。10 页夹具只有入场动画，所以「少 staging 前一页」在这份夹具上像素后果不可见——判据覆盖不到的地方，只能靠结构用例补，而不是假装夹具覆盖了。

## 5. 门禁

| 用例 / 命令 | 钉住什么 |
|---|---|
| `TestSegmentKeys*`（9 条） | 改一页只失效该页与后继；页序号不参与键；无转场页不吃前一页；改渲染器版本/CRF/Chrome 全失效；`nil` 与 `[]` 同键；0ms 等同 none；派生/审计字段不进键 |
| `TestDirSegmentCache*`（6 条） | 字节往返；非法键拒绝；并发同键不留半个文件；超限淘汰到水位且保留最新；空文件拒绝 |
| `TestSegmentCacheService*`（8 条） | 全命中零 backend 调用；部分命中只收到未命中页；截断缓存重渲；缓存全坏仍成功；降级页不入缓存；关缓存渲全部；计数正确；命中页不串页 |
| `TestStagePages*`（3 条） | staging 集合含转场前一页；只渲指定页；全命中时跳过 staging |
| `BenchmarkStageSinglePage` | 86.0ms/页，占单页渲染约 1% → 否决底图级缓存（ADR-4） |
| `go test ./internal/... ./cmd/...` | 42 包全绿 |
| `node --check renderer/render.mjs`、`degrade-check.mjs` | 7/7 |
| `cmd/render-perf` | 冷/二次/编辑/一致性/并行五个场景，一次跑完出上面全部数字 |

一致性是逐字节的：冷渲染 vs 关缓存 10/10 片段 SHA-256 相同；命中 vs 冷渲染 10/10 相同；增量渲 vs 同一份新计划的冷渲染 10/10 相同；并行 vs 串行逐页相同。成片 30.00s / 900 帧一致。

## 6. 没做的

- **S3/MinIO 缓存适配器**。`SegmentCache` 按对象存储语义定义（`Get`/`Put`），但只实现了本地目录。当前单机/共享卷够用。
- **缓存后台清理协程**。淘汰只在 `Put` 时触发，长期不写入就不收缩。
- **页并发默认值**。见 §3，留给 M4。
- **底图级缓存**（ADR-4）。省 86ms/页，不到单页耗时 1%，不值得多一层失效逻辑。
- **成片级缓存**（ADR-5）。全命中的尾部（拼接 + 混音）只有 2.0s，缓存一段成片换 2 秒，不划算。

## 7. 回滚

删掉 `ServiceConfig.SegmentCache` 的赋值（或 `-segment-cache` 置空）即回到「每页都渲」的旧行为，产物不变。缓存目录可以直接删，无副作用。
