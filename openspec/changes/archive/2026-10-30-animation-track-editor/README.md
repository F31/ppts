# 轨道编辑 + 灰度 + 额度（M4）落地说明

> 变更：`animation-track-editor`。对应里程碑 M4「轨道编辑与灰度」。
> 这份文档回答五个问题：**开放判定为什么只能有一个出口、额度为什么要跟账期绑在一起、
> 轨道拖动为什么必须改写触发器、配置怎么收口、回滚会失去什么。**

三段是分开落地的，可以分别回滚：

| 段 | 提交 | 内容 |
|---|---|---|
| 1 | `animation-rollout` | 能力判定收敛 + 灰度分桶 + 三处入口共用 |
| 2 | `animation-quota` | 渲染分钟额度：受理预占 / 按实际页结算 / 终态释放 |
| 3 | `animation-track-editing` | 元素级轨道时间轴：拖动、键盘微调、撤销 |

## 1. 为什么开放判定必须只有一个出口

M4 之前，「这个租户能不能用动画」分散在三处：写规格的 handler、导出选项接口、导出受理。
三处各读各的环境变量、各解释一遍 `tenants.policy`。这类分散判定的失败方式不是崩，是**答案不一致**：

- 导出选项说 `enabled=true` → 前端给出动画选项；
- 受理处读的是旧的环境变量 → 产出静态版；
- 用户看到的是「我明明开了动画，出来的是静态片」，且没有任何错误。

现在只有一个纯函数 `animation.AnimationPolicy.Resolve`：输入「租户 ID + 部署配置 + 租户策略」，
输出一份能力快照。**无 I/O、无全局状态**，所以它能被表驱动用例钉死，而不是靠「三处都记得改」。

优先级：**部署闸 > 租户显式 > 租户灰度 > 部署默认**。三条硬规则：

1. **部署闸关着，租户策略写 `enabled:true` 也没用**（`reason=deploy_disabled`）。机器没能力，
   不是权限问题。
2. **显式 `false` 压过 100% 的灰度**。封禁的租户不能因为放量被重新打开。
3. **策略读不出来时 fail closed**（`reason=policy_unreadable`）。读不到配置等于不知道，
   不知道就不给——放量阶段的默认值必须是「关」。

灰度用 SHA-256 分桶（`salt + "\x00" + tenantID`），不是 `hash/fnv` + 取模：
租户 ID 多是 `t_000123` 这种有序短串，弱雪崩哈希在小模数下会聚集，表现为「放量 30%，
实际开了 8%」。加 `\x00` 分隔是为了避免 `salt="ab"+tenant="c"` 与 `salt="a"+tenant="bc"` 撞桶。

## 2. 额度为什么要跟账期绑在一起

额度功能存在的唯一理由是**防超卖**，所以它必须是一次原子的条件更新。这里有个容易走错的岔路：

```
✗ 给 tenant_quotas 加 period 字段，跨月时在事务外判断「这个月是不是新月份」再决定重置
  → 两个并发的月末请求都判断为「跨月」，各自重置 → 双花
```

选的是把账期**编进计量种类**：

```
usage_kind = "animation_minutes:2026-10"
```

跨月天然就是 `tenant_quotas` 里的一个新行，`Reserve` 的单行条件更新仍然原子；上个月的行留在原处
供对账。代价是月度汇总要按前缀聚合（`WHERE usage_kind LIKE 'animation_minutes:%'`），
不能等值匹配——写进部署文档了，因为这是个会被写错的地方。

账期一律按 **UTC** 算。用服务器本地时区的话，同一租户在不同时区的节点上会在不同瞬间重置，
「月初」变成一个每台机器都不同的时刻。

三个位置分工（ADR-8）：

| 位置 | 动作 | 为什么在这里 |
|---|---|---|
| 受理 `POST /api/projects/{id}/exports` | 预占 | 超限必须在这里拒（429）。放到 worker 里就是设计 §7.5 禁止的「静默排队」 |
| worker `ExportHandler` | 结算 | 只有渲完才知道哪几页真的出了动画 |
| 取消 / 失败终态 | 释放 | 钱没花，额度不能锁到月底 |

三条容易搞反的语义：

- **降级页不计费**：降级页播的是静态段，没花渲染分钟。
- **整体退回静态（`av == nil`）必须结算 0**：预占要有终结动作，否则额度被锁到账期结束。
  第一版写成 `av != nil && 降级页跳过`，整体静态时循环把整片时长都算成动画分钟——
  正是「渲染失败却被满额收费」。用例 `TestSettleAnimationMinutesReleasesHoldWhenFullyStatic` 守这条。
- **`OnFailed` 只在失败终态触发**：可重试的中间失败不释放。否则重试成功后结算找不到预占 = 漏账。

账期在预占与结算两侧都取**任务创建时间**：月末提交、月初跑完，两次要对上同一行。

### 迁移决策：`max_minutes` 未配置 = 不限量

设计 §10.3 写的是 60/月，代码默认是不限量（ADR-7）。理由与 ADR-3 同一条：
升级当天给所有存量租户加一道硬停，会挡住已经在用的人。60 是运营配置值，写进部署文档的收口步骤。

另一个刻意的选择：**每次受理都同步额度表**（不限量写 `-1`），而不是「只在配了上限时写」。
否则运营把 120 改回 0（不限量）后，上一版的 120 还留在额度行里继续卡人。

## 3. 轨道拖动为什么必须改写触发器

入场片段的 `startMs` 在编译期由**触发器**推导：`onEnter` → 页首，`withSegment:<id>` → 分段起始。
渲染器不读 `startMs`，只读触发器。

所以「把色块往后拖但不改触发器」的结果是**保存成功、成片一点没变、没有任何报错**：
界面动了、视频没动。这是这一级功能最容易踩的坑，而且它不会在任何门禁里自己暴露出来。

规则（ADR-9）：

- 拖动/微调**派生起点**的片段 → 同时写 `atTime:<startMs>`，title 里说明「已改为固定时间」；
- 只改**时长**（拖右边缘）→ 不动触发器。把「拉长一点」也变成「脱离朗读对齐」是过度反应；
- 一次拖拽只记**一步**撤销（pointerdown 记、pointermove 不记）。按像素记步会让撤销变成
  「一次撤 1ms」，撤二十次才回原处；
- 撤销还原快照时**保留当前 `revision`**。栈里的快照带的是「当时」的版本号，
  直接还原会让下一次保存发出过期的 `expectedRevision`，变成必然 409。

实现上撞到两个坑，都写进 design 了：

1. **指针捕获必须落在色块上**，不能落在 8px 的右边缘把手上——捕获会把后续 pointermove 全部
   重定向到捕获元素，捕在把手上时色块的 `onPointerMove` 永远收不到，表现是「拽把手色块不动」。
2. **页尾放不下时截断时长、保持起点**：用户拖的是右边缘，色块整体跳走会被当成拖错了对象。

## 4. 配置与收口

完整变量表与两步收口流程在 `deploy/renderer/README.md` 的「租户级开放与灰度」一节。要点：

```json
{"animation": {"enabled": true, "track_editor": true, "preview": true, "max_minutes": 120}}
```

- `PPTS_ANIMATION_ROLLOUT` 默认 **100**（刻意的：等于「部署闸开 = 所有租户可用」，
  与引入租户策略之前一致）。直接改成 0 会在升级瞬间关掉所有客户。
- `PPTS_ANIMATION_ROLLOUT_SALT` **写进配置后不要再改**：改盐等于重新洗牌，
  会把已吃到灰度的租户踢回未开放状态。
- `track_editor` 默认 **false**——这是按角色/套餐卖的能力位，缺省不给；
  子能力不能越过总闸，`enabled` 为假时写了也没用。

## 5. 判据（实测）

| 判据 | 实测 |
|---|---|
| 三处入口答案一致 | 显式关闭 → 导出选项 `enabled=false` + `reason`、写规格 404、读规格 200 |
| 显式 true 绕过 0% 灰度 | 能力为真，`source=tenant` |
| 显式 false 压过 100% 灰度 | 能力为假 |
| 策略不可读 | `policy_unreadable`，fail closed |
| 预占 | 时间轴 300s → `reserved=5.000` 分钟 |
| 超限 | 上限 4 < 5 → 429，body 带上限/已用/申请量/`resetAt` + `Retry-After`，**不建任务** |
| 不超卖 | 30 并发、上限 10、每单 4 分钟 → **只成功 2 单，预占合计 8** |
| 降级页不计费 | 10s+20s+30s 三页、第 2 页降级 → 结算 40s = 0.667 分钟 |
| 整体退回静态 | 结算 0 |
| 跨月 | 按任务创建时间落到 `animation_minutes:2026-09` |
| 改上限 | 改成不限量 → 下一次导出即 201，额度行 `limit=-1` |
| 轨道拖动 | 派生起点片段拖动后 `trigger` 变为 `atTime:<ms>`（用例守「只改 `startMs` 不生效」） |
| 撤销 | 栈深 24，还原后 `revision` 保持当前值 |

门禁：`go build ./... && go vet ./...` 通过、`go test ./internal/... ./cmd/...` 全绿（42 包）、
`tsc -b` 通过、`vite build` 通过、`animation-check` 26/26、`i18n-check` 中英 1333/1333、
`contrast.mjs` 全绿、`openspec validate --all` 9 passed / 0 failed。

## 6. 不做（明确移出范围）

- **批量套用**（§7.6「页列表多选 → 套用此页动效」）：需要页列表引入多选态，并把一份规格写进
  N 页（每页各有自己的 `revision`）；中途失败时「全成或全不成」的回滚语义没有确定。
  空状态文案已落地，功能留作独立变更。
- **关键帧级 props 编辑**：本段只做 clip 的起点与时长，props 由预设决定。
- **额度剩余量 UI / 自助提额**：额度不足时给 429 + 四个数 + 恢复时间，提额走既有 `SetLimit` 管理面。
- **周期滚动任务**：账期在计量种类里，跨月不需要任何后台任务去重置。
- **按用户灰度**：只做到租户粒度。用户粒度需要稳定的用户标识参与分桶，且封禁语义要重新定义。
- **`plan` 表 / `animation.brand_presets`**：套餐位目前就是 `tenants.policy` 里的几个布尔值，
  引入套餐表要连带定义「套餐变更时存量额度怎么算」，不是这一版能收口的。

## 7. 回滚影响

| 回滚到 | 会失去 | 不会坏 |
|---|---|---|
| 段 1 之前 | 租户级开放判定、灰度分桶；`PPTS_ANIMATION_ENABLED` 重新变回唯一开关 | 已写入的 `tenants.policy` 留着无害，旧代码不读 |
| 段 2 之前 | 额度预占与结算；导出不再受分钟数限制 | 三张台账表留着无害；`usage_kind` 带后缀的行在旧代码里不会被读到 |
| 段 3 之前 | 轨道时间轴 UI 与撤销栈 | 已改成 `atTime:<ms>` 的规格仍然正确——`atTime` 本就是合法触发器，只是不能再靠朗读对齐 |

段 3 的回滚值得单独说：拖动过的片段已经被显式化了时间，回滚 UI 不会让它们变回派生起点。
这不是缺陷，是「显式化不可逆」的必然结果——想让它们重新跟随朗读，只能再改一次触发器。
