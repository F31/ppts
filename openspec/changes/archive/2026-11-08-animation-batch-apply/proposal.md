# 批量套用动效：把「选中的页一起改」做成全成或全不成

## 背景

设计方案 §7.6 留了一条交互要求：「页列表多选 → 套用此页动效，带撤销」。
M4 轨道编辑归档时把「批量套用」明确列为**独立变更**挂起，理由是它需要的不是多选 UI，
而是「N 页写入的失败回滚语义」（路线图 §1 变更表、`animation-track-editor` 归档记录）。

现状里已经有一个 `POST /animation/apply-all`：它是「一键成片」第三步，给**整份 deck 每页重新生成
默认规格**，逐页尽力而为、跳过人手改动页，单页失败降级成 `skipped` 继续跑。
这个语义对「一键成片」是对的（跑完 20 页比因为第 7 页失败而全盘皆输有用），
但对「我把第 3 页选了商务稳重，想让第 5/8/12 页也用这个风格」是错的：

> 用户勾选 5 页、点了套用，界面说「已套用」。实际只有 3 页写进去了，另外 2 页还是旧风格。
> 逐页编辑器不会提示「这两页没跟上」，成片里风格不一致，用户只能一页页去比对。

前端如果按 `apply-all` 的样子循环 2N 次单页请求，还会把「一批操作」拆成 N 个独立事务：
中途断网、页被别人锁了、第 4 页校验失败，都会留下一个没有名字、也没有出口的中间态。

**实现期实测纠正了一个想当然**。第一版按字面理解成「把源页已保存的规格（含 `tracks`）复制过去」，
Go 单测 9/9、前端门禁 7/7、全量构建全绿；但部署到 8077 用真实 22 页配音 deck 一跑，
3 个目标页**全部** `validation_failed`，零写入。根因是 V2：`Track.ElementID` 是页内形状 ID，
`Clip.trigger` 里的 `withSegment` 绑的也是本页分段 ID；不同页的形状 ID 本来就不重合，
跨页复制在语义上没有定义。单测之所以全绿，是因为所有夹具都给每页复用了同一批 `shape-1/2`。
这是典型的「门禁绿、真数据红」，也是本变更把语义收敛到**风格**的直接原因。

## 决策

1. **「套用」= 套风格，不是复制轨道**。源页只贡献 `presetId` 与 `intensity`；
   每个目标页走与「一键套用 / 单页打开选同一预设」完全相同的生成链
   （`bind.Run` 预填 → `animdefault.DefaultSpecReport` → `Revision.Validate`），
   用**自己的元素、自己的分段**重算轨道。这与 §7.6 空状态文案
   「当前使用『商务稳重』预设，点击调整」的语境一致。
2. **源页是自定义规格（`presetId` 为空）时整单拒绝**，说明请先在源页选一个预设；
   不静默退回默认预设——那不是「这一页的动效」。
3. **新增两个 REST 端点**：`POST /api/projects/{projectId}/animation/apply-batch` 与
   `.../apply-batch/restore`。请求带 `sourceSlideId`（风格来源页）+ `slideIds[]`（目标页），
   不引入新的 proto 契约（理由与 `apply-all` 一致，见 `web/route-inventory.json`）。
4. **契约是「全成或全不成」**：先预检所有目标页，任何一页不合格就整单
   `422 batch_ineligible` 并列出逐页原因，**一页都不写**；全部合格才由
   `animstore.ApplyBatch` 在**单事务**里提交；事务中发生并发冲突则整体回滚，
   不做补偿式「把写过的页改回去」。
5. **服务端给快照，前端一次撤销**：成功响应带 `previous[]`（写入前由服务端读取），
   `restore` 按快照单事务恢复；套用前没有规格的页用 `Rev=nil` 删行，而不是写一份空草稿。
6. **`locked` 永不越过**：审批终态即使 `overwrite=true` 也整单拒绝；`approved` 与有人工微调的页
   默认拒绝，显式 `overwrite` 才允许，且仍要过 V1–V12 校验与页时长检查。
7. **前端必须复核成功**：`applied` 汇总、逐页 `applied` 数、`previous` 快照数三者必须自洽，
   否则不显示「已套用」、不开放撤销按钮。

## 不做什么

- **不改 `apply-all`**。它的逐页降级是「一键成片」刻意要的语义，两条端点服务两种意图。
- **不复制源页的元素级微调、不复制 `Shots`**。前者锚在源页形状 ID 上，后者是源页 EMU 坐标，
  两者跨页都没有定义。要做「跨页复用一套编排」需要元素角色映射与分段重锚，是另一个变更。
- **不做多步撤销/重做栈**。本变更只提供**一次撤销**（最后一次批量套用）。
  §7.6 的「本地栈 ≥20 步」针对单页轨道微调，不在本变更范围。
- **不做模板另存 / 个人预设**（§7.6 另一条挂起项），源页只能是当前 deck 里已保存规格的页。
- **不做关键帧级 props 编辑、额度剩余量 UI、自助提额**（路线图既有挂起项）。
- **不覆盖 P1 埋点**。V18 编号冲突仍未订正，埋点边界按已确认的「仅在线分享上报」另立变更。

## 风险与边界

- **一次撤销是需要落库的**。§7.6 写「撤销/重做：本地栈，不落库」，但批量套用改的是 N 页数据库记录，
  浏览器本地栈撤不回来。因此本变更刻意偏离该条：快照由服务端生成，`restore` 是一次写事务。
  这是范围最小、可核验的偏离，已在 design 里写明理由。
- **快照由前端回传**。服务端只保证快照内容重新过 V1–V12、页 ID 属于当前 deck、单事务写入；
  它**不**校验这份快照确实来自某次特定的 apply-batch 调用。调用方在同一租户/项目内已具备规格写权限，
  这与既有 `PUT .../animation` 的权限边界相同；若将来要把撤销做成跨会话/跨设备能力，
  必须改成服务端按操作 ID 保管快照，不能沿用现在的无状态协议。
- **`Approved` 页在 `overwrite=true` 时会被写入新规格**；`animstore` 的 UPDATE 不改 `status` 列，
  因此状态仍是 `approved`。这是既有 `Put` 的语义，本变更不改它，但要在后续审批流变更里复核
  「换了内容却没重新审批」是否可接受。
- **并发**：预检与提交之间存在窗口，`ApplyBatch` 用 `expected revision` 兜底，
  窗口内被别人改过的页会让**整批** 409 回滚，用户需要重选重试，不会静默覆盖。
- **预填可能一条都绑不上**。此时 `animdefault` 会诚实产出空轨道（页面保持静态），
  与逐页编辑器选同一预设的结果一致；批量端点不额外猜一套兜底编排。
