# 提案：同帧门禁（V13）搬出渲染镜像——先有一份造得出来的成片

## 为什么做

`html-share-quality` 里唯一比「包端 vs 成片」的判据是 V13（`dom-ssim.py`）。它有两个问题，第二轮才发现它们其实是同一个：

1. **截图半边绑在 docker 上**。它要一个含 `chrome-headless-shell` 的镜像，而 Windows 上 docker 只存在于 WSL、路径要额外转换、镜像要另外构建。上一轮做 V13b 时本想把这一半切到新写的 `dom-shot.mjs`，结论是「本地没有可用的成片，改了也无法验证」——先放着。
2. **成片只能由渲染镜像产出**。MP4 分段要 Remotion + headless shell，本地同样没有。于是这条门禁的实际状态是「代码在、跑不起来、没人看」，而它守的恰恰是别的判据都守不住的那件事：两端是不是画的一样。

放着的代价不是「少一条判据」，是**这条判据的改动无法被检验**。要把它接回验证回路，必须先让「成片」在本地造得出来。

## 目标

1. **截图半边换成 `dom-shot.mjs`**：与 V13b 同一份实现（seek 落点、等图解码、摘掉外壳），删掉 docker、镜像参数与 WSL 路径转换里只服务截图的那部分。
2. **舞台钉在页图尺寸**：`dom-shot --stage WxH` 去掉播放器卡片的 1280 宽度上限，并**断言实测舞台就等于 W×H**（差 0.5px 都不行）。层位置本来就按画布百分比落位（`animation.ts` 的 `pct()`），去掉上限只是按原生尺寸再画一遍——实测 1920 页在 1920 舞台下与源页的 meanDiff 是 0.0007。
3. **夹具 `make-fixture.mjs`**：用 `share-baseline` 造包（走真实打包器），从清单派生 `plan.json`，按 30fps 逐帧截包自己的 DOM、裁剪到舞台、编码成逐页分段。于是「成片」在本地与 CI 都能复现。
4. **V13 进 CI**：挂在 `share-browser` 作业里，与 V16/V17/V13b 同一条流水线。
5. **V13b 顺带吃到同一套尺寸处理**：舞台改为按源页尺寸取，清单与页图尺寸不符时按输入问题退出（2），不再要求「包必须 ≤1280」。

## 非目标

- **不替代真实成片**。夹具的 MP4 来自包自身的 DOM，它证明的是「截图落点 / 抽帧 / 解码 / 阈值」这条管线，**不证明**包与真实渲染一致。后者只有真成片能答，判据与阈值一字未改。
- 不改判据：仍是逐页最差帧 ≥ 0.95，取样点仍是「首帧 / 第一段 clip 中点 / 末帧前一帧」。
- 不动 `still-check.py`。它只比两张 PNG，本身不依赖镜像；依赖渲染侧工具链的是它的上游 `renderer/still.mjs`（Remotion）。上一轮的路线图把两者并列写成「仍依赖渲染镜像」，是把输入当成了脚本。
- 不把 `dom-ssim.py` 的抽帧改成「一次 ffmpeg 抽全部帧」。逐帧调用够快（每帧 ~0.3s），换成滤镜图会让出错时的定位变难。

## 与既有变更的关系

- 依赖 `animation-settled-frame-gate`（已归档）留下的 `dom-shot.mjs`、`cdp.mjs` 与「摘外壳必须先 seek 之后」这条结论；
- 依赖 `animation-browser-gate-ci`（已归档）的浏览器解析（`PPT_CHROME` → 平台路径 → 兜底 headless-shell）；
- 与 `html-share-quality` 的现有规格有一处冲突需要改：那里写着「包与源页图 MUST 同尺寸……舞台宽度受播放器上限（1280）约束」，本轮把它换成「舞台 MUST 定成源页尺寸」。
